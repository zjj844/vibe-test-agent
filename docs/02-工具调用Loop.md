# 工具调用 Loop（图解）

> 读完这份，你应该能对着白纸画出这个 loop，并说清"谁在决定下一步"。

---

## 0. 先纠正一个误解：我们的 loop 不是"AI 自己挑工具"

很多人一听 Agent/loop，以为是这样：

```
❌ 错的想象（LLM 自主 tool calling）
   LLM ──想──► 我现在该调哪个工具？ ──► 调用 ──► 看结果 ──► 再想 ──► …
   （控制流在模型手里：不可复现、不可审计、没法写单测）
```

我们实际做的是：

```
✅ 真实的实现（固定编排 + 有界重试）
   代码决定顺序：探 → 读 → 写 → 评 → 跑 → 分 → 修 → 报
   模型只被"点名"干两件事：写测试、打分
   （控制流在代码里：可复现、可单测、每一步都能停下来看）
```

**一句话**：这里的"工具调用"指的是**代码调用我们写好的函数**，不是模型自己选函数。
**决策权在代码手里** —— 这是整个项目最重要的设计选择。

## 1. 五层架构（谁允许调用谁）

```
              ┌──────────────────────────────────────────┐
   编排层      │  loop.py（主循环）· main.py（总入口）        │  ← 决定"要不要再来一轮"
              └───────────────┬──────────────────────────┘
                              │ 只能向下调用 ↓
   ┌──────────────┬───────────┴──────────┬───────────────┐
   │ 能力层        │                      │               │
   │ generator.py │ critic.py            │ runner.py     │ triage.py
   │ （写用例）     │（给用例打分）          │（跑测试）      │（判失败归属）
   └──────┬───────┴──────────┬───────────┴───────┬───────┘
          │                  │                   │
   ┌──────┴──────────┐  ┌────┴─────────┐  ┌──────┴─────────┐
   │ 接口层            │  │ 接口层        │  │ 接口层          │
   │ targets.py（契约）│  │ http.py      │  │ （走 pytest）   │
   └──────┬──────────┘  └──────────────┘  └────────────────┘
          │
   ┌──────┴───────────────────────────────┐
   │ 基础设施层                             │
   │ retrieval/ · llm_client.py · env.py   │  ← 可替换：换嵌入、换模型
   └──────────────────────────────────────┘
```

**规则：箭头只能向下，不能向上。**
- `targets.py` 不知道有 generator 存在
- `http.py` 不知道有 triage 存在
- 所以换任何一层，其它层不用改

## 2. 一次完整循环（这才是"loop"）

```
                    START
                      │
                      ▼
            ┌──────────────────┐
            │ ① 探活 probe()    │  GET /api/health
            └────────┬─────────┘
                     │
        ┌────────────┴────────────┐
     失败│                        │成功
        ▼                         ▼
   ┌─────────┐          ┌──────────────────┐
   │ STOP    │          │ ② 读需求 kb.search│  检索需求文档
   │ 什么都   │          └────────┬─────────┘
   │ 不许改   │                   ▼
   └─────────┘          ┌──────────────────┐
                        │ ③ 写用例 generator│  契约 + 需求 → LLM 写
                        └────────┬─────────┘
                                 ▼
                        ┌──────────────────┐
                        │ 四道静态校验       │ 语法/形式/接口id/成员白名单
                        └────────┬─────────┘
                     ┌───────────┴───────────┐
                  违规│                       │通过
                     ▼                       ▼
            ┌─────────────────┐     ┌──────────────────┐
            │ 回喂违规原因重写  │     │ ④ 自评 critic     │  rubric 打分
            │ （最多 1 次）     │     │   2 次采样取中位   │
            └────────┬────────┘     └────────┬─────────┘
                     │                       │ 低分 → 打回重写（同一步）
                     └──────────► ③ ◄────────┤
                                             ▼高分
                                    ┌──────────────────┐
                                    │ ⑤ 落盘（先快照）    │ 写 test_generated.py
                                    └────────┬─────────┘
                                             ▼
                                    ┌──────────────────┐
                                    │ ⑥ 执行 runner      │ pytest → junitxml
                                    └────────┬─────────┘
                                             ▼
                                    ┌──────────────────┐
                                    │ ⑦ 分流 triage      │ 判定"这是谁的错"
                                    └────────┬─────────┘
                                             ▼
                          ┌──────────────────┼──────────────────┐
                          │                  │                  │
                    全部通过              可修类(FIX)        不可修类
                          │                  │            (STOP/缺陷)
                          ▼                  ▼                  ▼
                    ┌──────────┐    ┌─────────────────┐  ┌──────────────┐
                    │ ⑧ 出报告  │    │ 轮数 < 2 ?       │  │ ⑧ 出报告      │
                    │  DONE    │    │ 是 → 回去改，再来 │  │  + 缺陷清单   │
                    └──────────┘    │ 否 → 停手出报告   │  └──────────────┘
                                    └─────────────────┘
```

**背这个顺序**：**探 → 读 → 写 → 校验 → 评 → 存 → 跑 → 分 → 修（≤2 轮）→ 报**

## 3. 三个"闸门"（决定循环生死的地方）

| 闸门 | 位置 | 不过去会怎样 |
|---|---|---|
| **闸门 1：探活** | 最前面 | 服务没起 → **立即 STOP**，一个字节都不改 |
| **闸门 2：静态校验** | 落盘前 | 语法错/瞎编接口 → **回喂重写一次**；还不过就放弃 |
| **闸门 3：失败分流** | 执行后 | 是系统 Bug → **不许修**，只出缺陷报告 |

**三个闸门的共同作用**：让"自动修"只发生在**安全的范围**内。这就是自愈系统的安全边界。

---

## 4. 分流的五个出口（triage 的完整分支）

```
                       一条失败的用例
                             │
        ┌────────────┬───────┴────────┬────────────┬──────────┐
        ▼            ▼                ▼            ▼          ▼
   ① 服务不可达   ② 系统Bug      ③ 生成代码问题  ④ 断言问题  ⑤ 脚本问题
   ConnectionError  5xx / 结构不符  AttributeError  Assertion  KeyError
        │            │                │            │          │
        ▼            ▼                ▼            ▼          ▼
     STOP        REPORT_DEFECT    REGENERATE      FIX        FIX
   （停手）      （写缺陷报告）    （重新生成）    （可改）    （可改）
        │            │                │            │          │
        └────────────┴────────┬───────┴────────────┴──────────┘
                              ▼
                       进入下一轮（≤2）
```

**记住这条分界线**：左边两类**永远不改测试**；右边三类才允许动手。

---

## 5. 循环的边界（为什么必须有上限）

| 边界 | 值 | 为什么 |
|---|---|---|
| 生成重写次数 | 1 次 | 只在"可机器判定"的违规上重试；再多模型会敷衍 |
| 自愈轮数 | 2 轮 | 第 3 轮起收益递减、成本翻倍，且模型容易"把断言改弱以求通过" |
| 单次执行超时 | 900 秒 | 被测服务卡住时不能无限等 |

> 一句话：**没有上限的循环不是智能，是失控。** 上限是给自己留的止损点。

## 6. 数据在每个模块之间怎么流动

```
targets.py  ──Target──────────────► generator.py ──代码文本──► critic.py
     │                                    │                      │
     │ Endpoint                           │ 违规列表               │ 分数+评语
     ▼                                    ▼                      ▼
   http.py ──HttpResult──► 生成的测试文件 ──► runner.py ──RunResult──► triage.py
                                                                       │
                                                             Verdict（类别+动作）
                                                                       ▼
                                                                  report.py
```

**每个模块的输出都是一个小对象**（`Target` / `HttpResult` / `CaseResult` / `Verdict`）——
这就是"接口清楚"的具体含义：**下一层只依赖上层的对象，不依赖它的内部实现**。

---

## 7. 那"真正的 LLM tool calling"长什么样（如果你以后要升级）

```
模型收到工具清单 → 决定调哪个 → 我们执行 → 把结果塞回对话 → 模型再决定
```
适合：**步骤事先不确定**的任务（比如"随便帮我看看这个网站有什么问题"）。
不适合：**步骤固定**的任务（我们这条流水线就是固定的）。

我们的选择理由可以背下来：

> "我的流程是确定性的七步，加有界重试就够了。用模型来决定下一步，会带来三个问题：
> 不可复现（同一输入两次不同）、不可审计（出问题不知为何这么走）、不可测试（没法写单测）。
> 所以我把决策权留在代码里，只把'没有唯一答案'的两件事（写用例、打分）交给模型。"

## 8. 一次真实运行的完整轨迹（本项目实测数据）

```
① 探活        GET /api/health → 200          2 ms
② 读需求      命中 3 个片段                    （本地检索）
③ 写用例      deepseek-flash 生成 3 条         ~10 s（首次）
   静态校验    第一次违规：r.json() 不存在       → 回喂 → 第二次通过
④ 自评        3.80/5（2 次采样取中位）         ~8 s
⑤ 落盘        上一批自动归档 → 只留当前批次
⑥ 执行        pytest → 3 passed               4.68 s
⑦ 分流        无失败 → 无需进入第二轮
⑧ 报告（待实现 report.py）
```

**整个循环只用了 2 个 LLM 调用点**（写用例、打分），其余全是确定性代码。
