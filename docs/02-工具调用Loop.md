# 工具调用 Loop（图解）

> 读完这份，你应该能对着白纸画出这个 loop，并说清"谁在决定下一步"。

---

## 0. 先纠正一个误解：我们的 loop 不是"AI 自己挑工具"

很多人一听 Agent/loop，以为是这样：

```
❌ 错的想象（LLM 自主 tool calling）
   LLM ──想──► 我现在该调哪个工具？ ──► 调用 ──► 看结果 ──► 再想 ──► …
   （控制流在模型手里：不可复现、不可审计、没法写单测）
```

我们实际做的是：

```
✅ 真实的实现（固定编排 + 有界重试）
   代码决定顺序：探 → 读 → 写 → 校验 → 评 → 快照 → 跑 → 分 → 定 → 报
   模型只在三个位置被"点名"：写测试、打分、以及规则判不了时给一句建议
   （控制流在代码里：可复现、可单测、每一步都能停下来看）
```

**一句话**：这里的"工具调用"指的是**代码调用我们写好的函数**，不是模型自己选函数。
**决策权在代码手里** —— 这是整个项目最重要的设计选择。

## 1. 五层架构（谁允许调用谁）

```
              ┌────────────────────────────────────────────────────────┐
   编排层      │  loop.py（主循环：十步 + 决策）                          │  ← 决定"要不要再来一轮"
              │  server.py（报告台：只读视图 + 一键运行，不是平台）        │
              └───────────────┬────────────────────────────────────────┘
                              │ 只能向下调用 ↓
   ┌──────────┬──────────────┴───────────┬──────────────┬──────────────┐
   │ 能力层    │                          │              │              │
   │generator │ critic.py                │ runner.py    │ triage.py    │ advisor.py
   │（写用例） │（给用例打分）             │（跑测试）     │（判失败归属） │（规则判不了才问）
   └────┬─────┴──────────┬───────────────┴──────┬───────┴───────┬──────┴─────┘
        │                │                      │               │
   ┌────┴────────┐  ┌────┴─────────┐   ┌────────┴────┐  ┌───────┴──────────┐
   │ 接口层       │  │ 接口层        │   │（走 pytest） │  │ 契约/需求层       │
   │ targets.py  │  │ http.py      │   │             │  │ kb.py + vectordb │
   │ bootstrap.py│  │（自动注入token）│   │             │  │（分块/索引/检索） │
   └────┬────────┘  └──────────────┘   └─────────────┘  └───────┬──────────┘
        │                                                        │
   ┌────┴────────────────────────────────────────────────────────┴────────┐
   │ 基础设施层                                                             │
   │ retrieval/（chunking/embedding/store/retriever）· llm_client.py · env.py │  ← 可替换：换嵌入、换模型
   └──────────────────────────────────────────────────────────────────────┘
```

**规则：箭头只能向下，不能向上。**
- `targets.py` 不知道有 generator 存在
- `http.py` 不知道有 triage 存在
- 所以换任何一层，其它层不用改

**背这个顺序**：**探 → 读 → 写 → 校验 → 评 → 快照 → 跑 → 分 → 定 → 报**

## 3. 四个"闸门"（决定循环生死的地方）

| 闸门 | 位置 | 不过去会怎样 |
|---|---|---|
| **闸门 1：探活** | 最前面 | 服务没起 → **立即 STOP**，一个字节都不改，一次模型都不调 |
| **闸门 2：静态校验** | 落盘前 | 语法错/瞎编接口/用了不存在的成员 → **回喂重写一次**；还不过就放弃本批 |
| **闸门 3：失败分流** | 执行后 | 是系统 Bug 或契约不一致 → **不许改测试**，只出报告交人 |
| **闸门 4：模型权限** | 归因 | 模型只产出一段文字建议，**没有任何可执行字段**，决策仍在代码里 |

**四个闸门的共同作用**：让"自动修"只发生在**安全的范围**内。这就是自愈系统的安全边界。

## 4. 分流的六个出口（triage 的完整分支）

```
                       一条失败的用例
                             │
   ┌──────────┬──────────────┼──────────────┬───────────┬──────────┐
   ▼          ▼              ▼              ▼           ▼          ▼
①服务不可达  ②系统Bug     ②'业务码5xx    ③契约不一致  ④生成代码   ⑤断言/脚本
Connection    HTTP 5xx    body.code=5xx  HTTP 200 但   Attribute   Assertion/
Error                      （后端异常兜底） 数据不符      Error      KeyError
   │          │              │              │           │          │
   ▼          ▼              ▼              ▼           ▼          ▼
  STOP   REPORT_DEFECT  REPORT_DEFECT     HOLD      REGENERATE    FIX
（停手）（出缺陷清单）  （先核对参数/契约）（挂起交人）（重新生成）（可改）
```

**记住这两条分界线**：
- 左边四类**永远不改测试**（服务不可达 / HTTP 5xx / 业务码 5xx / 契约不一致）
- 只有右边两类（生成代码问题、断言/脚本问题）才允许动手

> 为什么 ②'（HTTP 通了但 body.code=5xx）要单列：很多国内后端用 body.code 表达业务错误，
> HTTP 仍返 200。之前这种情况会被判成"断言写错"去改测试 —— 而归因错了，锅在服务端或契约。

## 5. 循环的边界（为什么必须有上限）

| 边界 | 值 | 为什么 |
|---|---|---|
| 生成重写次数 | 1 次 | 只在"可机器判定"的违规上重试；再多模型会敷衍 |
| 自愈轮数 | 2 轮 | 第 3 轮起收益递减、成本翻倍，且模型容易"把断言改弱以求通过" |
| 单次执行超时 | 900 秒 | 被测服务卡住时不能无限等 |
| 生成 token 预算 | 14000（空正文自动放大到 32000 再试一次） | 推理模型会把预算吃光，正文为空 |
| 模型调用次数 | 每轮 ≤ 5（生成 1~2 + 评分 2 + 归因 0~2） | 成本可控、最坏时长可估算 |

> 一句话：**没有上限的循环不是智能，是失控。** 上限是给自己留的止损点。

## 6. 数据在每个模块之间怎么流动

```
targets.py ──Target────────────► kb.py ──检索片段──┐
    │                            (vectordb 索引)   │
    │ Endpoint                                     ▼
    ▼                                    generator.py ──代码文本──► critic.py
  http.py ──HttpResult──► 生成的测试文件 ──► runner.py ──RunResult──► triage.py
                                                                        │
                                                          Verdict（类别+动作）
                                                                        ▼
                                              triage ──► advisor（只对 MANUAL/HOLD）
                                                                        │
                                                                        ▼
                                                                   report.py
```

**每个模块的输出都是一个小对象**（`Target` / `HttpResult` / `CaseResult` / `Verdict` / `Hit` / `Advice`）——
这就是"接口清楚"的具体含义：**下一层只依赖上层的对象，不依赖它的内部实现**。

## 7. 那"真正的 LLM tool calling"长什么样（如果你以后要升级）

```
模型收到工具清单 → 决定调哪个 → 我们执行 → 把结果塞回对话 → 模型再决定
```
适合：**步骤事先不确定**的任务（比如"随便帮我看看这个网站有什么问题"）。
不适合：**步骤固定**的任务（我们这条流水线就是固定的）。

我们的选择理由可以背下来：

> "我的流程是确定性的十步，加有界重试就够了。用模型来决定下一步，会带来三个问题：
> 不可复现（同一输入两次不同）、不可审计（出问题不知为何这么走）、不可测试（没法写单测）。
> 所以我把决策权留在代码里，只把'没有唯一答案'的三件事交给模型：
> 写用例、打分、以及在规则判不了时给一句建议（且没有动作权限）。"

## 8. 一次真实运行的完整轨迹（本项目实测数据）

```
① 探活        GET /api/article/page → 200            4 ms
② 读需求      命中 3 个片段：PRD#s36、PRD#s28、规范·日志规约   （hybrid 检索，206 块）
③ 写用例      deepseek-flash 生成 3 条                ~10 s（首次）
   静态校验    第一次违规：r.json() 不存在              → 回喂 → 第二次通过
④ 自评        3.70/5（2 次采样取中位）                ~8 s
⑤ 落盘+快照   上一批进 _archive/，本轮留回滚点
⑥ 执行        pytest → 2 passed / 1 failed            1.1 s
⑦ 分流        断言问题 1
⑧ 兜底归因    规则判不了的那条才问模型（2.5 s），只写建议
⑨ 决策        可修失败 1 条 → 带上失败摘要进入第 2 轮
⑩ 报告        第 2 轮 3/3 → ✅ success，报告写入 reports/
```

**整个循环用到的 LLM 调用点**：写用例（1~2 次）、打分（2 次）、兜底归因（0~2 次），其余全是确定性代码。
