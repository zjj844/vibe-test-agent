# 新项目接入指南（6 步 + 三个坑）

> 场景：你有一个新项目要测，手上只有它的源码/接口文档。
> 这份文档是**照着做就能跑通**的流程，以及每一步为什么这么做。

---

## 一、6 步流程

```bash
# ① 起服务，确认能访问（探活接口要 200）
python -m selfheal.targets --target <你的项目>   # 此时还没有契约，跳过这步
```

### 步骤 1：导入项目（起草契约）

打开报告台 **http://127.0.0.1:8100/** → 顶栏「＋ 导入新项目」：

| 字段 | 填什么 |
|---|---|
| 项目名 | 小写字母/数字/连字符，如 `my-app` |
| 服务地址 | 如 `http://127.0.0.1:9000`（**别带 `/cms` 之类的 context 除非确实有**） |
| 源码文件 | 选该项目的 **Controller** 文件（Java/Python/C#/Go 都行，模型读代码，不写解析器） |

点【AI 起草契约】，等 10~20 秒，得到一张接口表格。

### 步骤 2：看体检警告（这一步很多人跳过，然后跑出 0%）

起草/保存时工具会提示四类问题，**逐条处理**：

| 警告 | 含义 | 处理 |
|---|---|---|
| `N 个接口的说明里写着「需要登录」，但契约没有 auth 配置` | 这些接口会全拿到 `code=401` | 补 `auth`（起草已自动推断，核对 `endpoint` 是否指向登录接口即可） |
| `登录接口没有请求体(body)` | 裸调用登录会 400/500 | 补真实账号密码，如 `{"username":"admin","password":"123456"}` |
| `N 个写操作接口没有请求体(body)` | **POST/PUT/DELETE 没 body → 必然 400/500** | 见步骤 3：删掉或补参数 |
| `health 指向 POST 接口` | 探活会不稳 | 换一个不需要登录、不需要参数的 GET 接口 |

### 步骤 3：收窄契约（口语叫"瘦身"）

**契约不是"API 目录"，是"这一轮要测的范围"。**

| 保留 | 删掉（或移到另一份契约） |
|---|---|
| 只读查询（列表/详情/树） | 需要业务参数的写操作（新增文章、分配角色、上传文件） |
| 登录（有 body） | 需要前置数据的操作（审核=要先有文章） |
| 一条**鉴权边界**（同一接口 + `no_auth`，期望 `code=401`） | 调试/统计/测试专用接口 |

**建议规模：6~10 个接口。** 然后 `--n 8` 让它基本全覆盖。

### 步骤 4：粘需求文档（可选但强烈建议）

面板下半部分「需求文档」→ 粘贴 PRD → 保存。

- 保存时会**自动**把 `requirements_dir` 写进契约
- 用 `## FR-1 xxx` 或 `FR-1 xxx` / `一、xxx` 分节（三种都支持，分节标题就是切块依据）
- 有需求文档 vs 没有，自评会差 3.2 vs 4.2

### 步骤 5：接外部规范（可选）

在契约里加一行：

```json
"external_docs": "corpus_external"
```

效果：检索变成"需求 + 组织规范"混合检索（SQLite 索引 + BM25 + 向量 RRF，外部规范占 1 个配额）。

外部规范语料用脚本拉：

```bash
python scripts/fetch_external_corpus.py      # 17 篇 / 157 块（阿里的开发手册等）
python scripts/eval_retrieval.py --md        # 出 recall@3 / MRR 数字到 docs/07
```

### 步骤 6：跑，然后看报告而不是看通过率

```bash
python -m selfheal.loop --target my-app --n 8 --rounds 2
```

报告分四节，按这个顺序看：

1. **缺陷清单** → 服务端 5xx，提单给后端
2. **需人工确认** → HTTP 通了但数据不符，核对"服务错 / 契约错 / 用例错"
3. **可修类失败** → 脚本/断言问题，工具会自己重写（≤2 轮）
4. **AI 辅助判断** → 规则判不了时的一段建议（无动作权限）

## 二、三个必踩的坑（我们都踩过）

### 坑 1：喂错语料 → 检索到"别的项目"的需求

**现象**：报告里 `读需求 检索到：REQ-001-问答页面…`（不是你的 PRD）。
**原因**：契约里没配 `requirements_dir`，工具退回到默认目录。
**修法**：走一遍「保存需求文档」（会自动补字段），或手写 `"requirements_dir": "selfheal/requirements_docs/<项目>"`。

### 坑 2：写操作没 body → 每次都 500

**现象**：`{"code":500,"msg":"系统繁忙"}`，或被判成"系统缺陷"。
**原因**：工具**不会替你编业务参数**（编出来的数据等于造假用例）。
**修法**：删掉这些接口，或者补上真实 body。

### 坑 3：推理模型把 token 预算吃光 → 第 2 轮生成失败

**现象**：`模型正文为空：max_tokens 被推理过程吃光（reasoning_tokens=8000）`。
**原因**：第 2 轮提示词更长（上一版代码 + 失败摘要），推理模型的思考长度随输入上升。
**现状**：已三层兜底（默认 14000 → 空正文自动放大到 32000 → 再精简历史）。可用 `QA_GEN_MAX_TOKENS` 调。

## 三、失败变多 ≠ 变差（怎么判断）

| 原因 | 能否靠"跑更多用例"解决 |
|---|---|
| 契约接口数 ≫ `--n` → 覆盖摊薄 | ✅ 能，加大 `--n` |
| 契约信息不足（写操作没 body） | ❌ 不能，跑 100 条也一样 |
| 需求与实现真的不一致 | ❌ 不能，只能人裁决 |

**实证**（同一份配置只改接口集）：
- 8 个只读接口 + `--n 8` → **6/8 通过**
- 同样 8 个 + 4 个无 body 写操作 → **4/8 通过**（多出来的失败正好是那两个写操作）

## 四、三方裁决表（报告出红时按这个查）

| 谁 | 该问的问题 | 结论 |
|---|---|---|
| **实现** | 接口返回的东西符合团队约定吗？ | 补实现 / 提单 |
| **契约/PRD** | 这条要求是"必须"还是"建议"？其他端怎么取这个数据？ | 改文档 |
| **用例** | 断言是不是硬编码了某个具体值（11、id=1、999）？ | 改断言（工具会重写，但也能人工改） |

> 示例（真实发生）：PRD 要求"登录返回 11 个权限码"，实测 `/api/auth/login` 只返回 `token+user`，
> 11 个 `perms` 在 `/api/auth/info` 里 → 要么 login 补 `perms`，要么改 PRD 口径。

### ⚠️ PRD 的来源，决定了对齐质量

实测对比（同一个项目，两份不同来源的 PRD）：

| PRD 来源 | 结果 | 原因 |
|---|---|---|
| **老师给的课程设计说明书**（理想方案） | 大量失败，且多为"需求与实现不一致" | 说明书里有些方案**项目并没实现**（如登录直接返回权限码集合）→ 按它写断言必然红 |
| **按项目实际实现重写的 PRD**（验收口径） | 顺利通过 | 条款和实现对得上，"该测什么"是有效的 |

**结论：PRD 必须是"验收口径"，不是"设计愿景"。** 如果手上有的是设计文档，
先花 10 分钟把它对齐到实现（做不到的条款要么删、要么标注"未实现"），再拿来喂工具。
这不是工具的问题——用理想需求去测现实代码，本来就该红。

---

## 五、一句话总结

**导入 → 看体检 → 收窄到 6~10 个接口 → 粘需求 →（可选）接外部规范 → 跑并看报告归因。**
契约是配置，定一次长期用；不要把"每次跑"和"每次改契约"混为一谈。
