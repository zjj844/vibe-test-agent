# 零基础入门：这个项目到底在干嘛

> **先读这一份，再读 `01-MVP架构设计.md`。**
> 本文假设你什么术语都不懂。每个术语第一次出现都会用括号解释。
> 读完你能对着一张白纸讲清这个项目——这就是面试需要的程度。

---

## 0. 先用一个故事把全流程串一遍

想象你开了一家**自动判卷的考试中心**。

1. 有个学生（= **被测软件**，比如你的 RAG 后端、你的 Java CMS）来报名。
2. 你拿出一份**考纲**（= `configs/rag-backend.json`），上面写着"要考哪些知识点"。
3. **监考先检查考场开门了没**（= **探活**：发一个最小请求，确认服务活着）。
   - 门没开 → **今天就别考了**，一个字节都别改。为什么？见 §3。
4. **出题老师**（= LLM）照着考纲和教材（= **需求文档**）出题，题目就是**测试用例**。
5. **审题老师**（= `critic.py`）检查题目合不合格：太简单的打回重出。
6. **开考**（= 跑 pytest），学生答卷。
7. **判卷老师**（= `triage.py`）看每道错题：**是学生答错了，还是题目本身出错了？**
   - 题目出错 → 改题目（自动改）
   - 学生答错 → **不许改题**，登记成"缺陷"，交给人看
8. **改卷子前先存档**（= `snapshot.py`），改坏了能一键还原。
9. **补考**：最多再来 2 轮（有上限，见 §3）。
10. **出成绩单**（= `report.py`）：通过率、错题分类、缺陷清单。

**这张故事里唯一反直觉、也最重要的一步是第 7 步。** 后面会反复讲。

## 1. 四件最基础的事（每件都说清"没有它会怎样"）

### 1.1 HTTP 与接口

- **HTTP** 就是浏览器/程序跟服务器说话的方式。一次说话 = 请求 + 响应。
- **接口**（API）是服务器开的一个"办事窗口"。窗口有名字（`/api/ask`）和规矩（要用 POST、要带什么参数）。
  类比：去政务大厅办事，不同的窗口办不同的事，窗口号就是接口路径。

**没有它会怎样**：你的程序只能给人点了看，没法被机器自动测试。

### 1.2 契约（contract）

- **契约** = 一份写下来的约定："调这个接口，应该返回 200，JSON 里应该有 `answer` 和 `citations` 这两个字段"。
- 有了契约，测试才有**判断标准**；没有契约，你只能测"程序没崩"。

**没有它会怎样**：AI 只能瞎猜该期待什么，测试写得毫无意义。

### 1.3 测试与断言（assert）

- **测试** = 一条可重复执行的检查。
- **断言**（assert）= 检查里那句"必须成立"的话。`assert 状态码 == 200` 的意思是"如果不是 200，就当场报错"。
- 类比：验货单。`assert 箱子里有 12 瓶` —— 不是 12 瓶就退货。

**没有它会怎样**：你只能靠肉眼点页面，改一次代码就要重看一遍，累死且漏。

### 1.4 pytest

- **pytest** 是一个"自动跑验货单的机器"。你把检查写成 `def test_xxx():` 的函数，它全跑一遍，告诉你几绿几红。

**没有它会怎样**：你得手动一个个调用，还得自己数结果。

## 2. LLM（大模型）在这个项目里到底干什么

**把它当成一个"会说人话、但靠不住的实习生"。**

| 它擅长 | 它不擅长 |
|---|---|
| 读需求，写出像样的测试代码 | 保证代码能跑 |
| 解释一段错误信息 | 判断"这是接口坏了还是测试写错了" |

所以项目里的规矩是：

1. **让它写，但用确定性的规则校验它**（语法检查、接口契约检查）—— 机器能判的，不要问它。
2. **让它自评，但用固定评分表（rubric）** —— 否则每次打分都不一样，无法比较。
3. **不让它决定"要不要改"** —— 这个决定必须由**规则**做（见 §3）。

---

## 3. "自愈"到底是什么（最容易误解的一点）

很多人以为自愈 = "AI 自己修 bug"。**错。**

**自愈 = 失败先分类，只在安全范围内动手。**

| 失败类别 | 举例 | 允许怎么做 |
|---|---|---|
| ① 服务不可达 | 服务根本没启动 | **什么都不许改**，重新起服务 |
| ② 系统 Bug | 返回 500、返回结构不对 | **不许改测试**，写缺陷报告给人 |
| ③ 脚本问题 | 接口路径写错了 | 可以改测试 |
| ④ 断言问题 | 返回正常但期望值写错了 | 可以改测试 |
| ⑤ 生成代码问题 | 代码有语法错、调用了不存在的方法 | 重新生成这段代码 |

### 为什么②明明能"改成通过"，却偏不改？

因为那是**作弊**。

> 假设接口真的坏了（返回 500），你把测试改成"期望 500"——测试立刻变绿，Bug 却还在线上。
> **缺陷被掩盖，比漏测危险得多。**

所以自愈系统的第一条规则**不是"怎么修"，而是"哪些不许修"**。
这也是为什么自愈轮数要有上限（2 轮）：轮数越多，模型越容易"为了让测试通过而把断言改弱"。

## 4. 端到端时序（跑一条命令，内部发生 12 件事）

```
1. 你敲命令：python -m selfheal.main --target rag-backend
2. 读考纲：把 rag-backend.json 读成对象（4 个接口）
3. 探活：GET /api/health，确认服务活着
      └ 挂了 → 打印"服务未启动"，结束（不写不跑不改）
4. 读需求：从需求文档里检索出"这个接口该满足什么业务规则"
5. 出题：把「契约 + 需求片段」交给 LLM，让它写 pytest 用例
6. 审题：LLM 按 rubric 自评（2 次取中位），低于分就打回重出
7. 落盘：把用例写成 test_generated.py（写之前先快照）
8. 开考：跑 pytest，产出 junitxml（一份机读的成绩记录）
9. 判卷：把每条失败分成 5 类（见 §3 的表）
10. 修复：只对 ③④ 类动手，改前快照，改完重跑
11. 补考：轮数 < 2 就回到第 8 步，否则停
12. 出成绩单：REPORT-时间.md（通过率 / 分类统计 / 缺陷清单）
```

## 5. 术语小词典（一行一个）

| 术语 | 一句话解释 |
|---|---|
| **接口 / API** | 服务器开的一个办事窗口，有路径和规矩 |
| **契约** | 写下来的约定：调它该返回什么 |
| **探活** | 发一个最小请求，确认服务活着 |
| **断言 / assert** | "必须成立"的那句话，不成立就报错 |
| **测试用例** | 一条可重复执行的检查 |
| **pytest** | 自动跑用例的机器 |
| **traceback** | 程序崩了时打印的那一大段错误信息 |
| **junitxml** | pytest 产出的机读版成绩单（XML 格式） |
| **失败分流** | 把失败按原因分成几类，不同类不同处理 |
| **快照 / 回滚** | 改文件前先备份；改坏了还原 |
| **rubric** | 固定的评分表（几个维度、每维几分） |
| **Prompt / 提示词** | 你发给大模型的那段话 |
| **RAG** | 先查资料再回答的做法（本项目用它查需求文档） |
| **嵌入 / 向量** | 把文字变成数字串，意思相近的数字也相近 |
| **幂等** | 同样的请求做多次，结果一样（POST 通常不幂等，这点要小心） |

## 6. 学习检验清单（能答上 8 题就算真懂了）

> **先自己答一遍再看答案**——答题才是检验，看答案只能背。

1. 为什么探活失败时"一个字节都不许改"？
2. 契约和测试用例的关系是什么？（谁给谁提供判断标准）
3. `assert` 用来干什么？举一个你项目里的 assert。
4. pytest 是怎么知道"该跑哪些函数"的？
5. 大模型在这个项目里负责"写"，那"判断"是谁负责？
6. 失败分 5 类，说出其中 3 类。
7. 为什么"接口返回 500"时不许改测试？
8. 为什么自愈只允许 2 轮，不是无限轮？
9. 快照是干什么的？什么时机做快照最重要？
10. 为什么评分要"2 次取中位"？

---

### 参考答案

**1. 为什么探活失败时"一个字节都不许改"**
服务没起来 → 所有用例都会红，但**这些红不是用例的错**。
此时去改用例，等于**把好用例改坏**，而且真正的故障（服务没起）被掩盖。
→ 规则：**先报"服务不可达"，什么都不动。**

**2. 契约和测试用例的关系**
**契约给用例提供判断标准**，用例不自己发明期望。
契约 = 点菜单（该给我什么）；用例 = 验货单（有没有按菜单给）。
项目里的体现：用例从 `rag-backend.json` 读 `expect_status` 和 `expect_fields`。

**3. assert 用来干什么**
`assert` 是"必须成立"的检查，不成立立刻抛 `AssertionError`（测试变红）。
例：`assert body["citation_valid"] is True, "引用校验未通过"`

**4. pytest 怎么知道该跑哪些函数**
**按命名约定自动发现**：文件 `test_*.py`、函数 `test_*`，
在 `testpaths` 指定目录下递归收集。不需要注册、不需要列清单。

**5. 大模型负责"写"，判断谁负责 ⭐**
**机器负责判断。**
- 断言 → `assert`（确定性代码）
- 失败分流 → 规则匹配 traceback（不是让模型分类）
- 只有"规则判不了"的才留给模型（v2）

→ 一句话：**能确定性判定的，不问模型。**

**6. 失败 5 类（任说 3 类即可）**
① 服务不可达　② 系统 Bug（5xx / 结构不符）　③ 脚本问题（路径 / 字段名错）
④ 断言问题（期望值错）　⑤ 生成代码问题（语法错 / 调用不存在的方法）

**7. 为什么 500 不许改测试 ⭐**
因为那是**接口真的坏了**。把期望改成 500、或删掉断言，测试立刻变绿——但 **Bug 还在线上**。
→ **掩盖缺陷比漏测危险得多。**

**8. 为什么自愈只 2 轮 ⭐**
① **收益递减**：第 3 轮起基本是瞎改
② **成本翻倍**：每轮都要跑测试 + 调模型
③ **风险递增**：轮数越多，模型越倾向"把断言改弱以求通过"
→ 设上限 = **给自己一个止损点**。

**9. 快照干什么，什么时机最重要**
改文件**之前**备份，改坏了能一键还原。
最重要时机是**第一次写/改之前**——那是唯一能还原的时点。
→ **事后备份等于没有。**

**10. 为什么评分 2 次取中位**
LLM 打分有抖动（同一份代码两次可能差 1 分）。
**单次打分不可比较**；2 次取中位能把单次异常拉回来，让分数**可复现**。

### ⭐ 面试杀手题：1、5、7、8

**追问链 A（针对第 5 题）**
> 问："那你系统里的模型到底干嘛？"
> 答："它只干两件事：读需求写用例、按 rubric 自评。**判断类的一律不用它**——模型的判断不可复现、不可审计，出了问题没人能复核。"

**追问链 B（针对第 7 题）**

### 一页背诵版（面试前看这段）

```
1  探活失败 → 一个字节都不改（红不是用例的错）
2  契约给用例提供判断标准（点菜单 vs 验货单）
3  assert = 必须成立那句话

5  模型只管写，判断交给机器（能确定性判定的不问模型）

7  500 不许改测试（掩盖缺陷比漏测危险）

9  快照在改之前做（事后备份等于没有）
10 打分 2 次取中位（单次不可比较）
```

## 7. 你在项目里的角色（这条能缓解焦虑）

**你不是程序员，你是产品经理 + 验收员。**

| 你负责 | AI 负责 |
|---|---|
| 说清要什么、界定范围、判断"这算不算做完" | 写代码 |
| **逐段读懂**，能讲出"为什么这么写" | 解释它写的每一段 |
| 定判据（什么算通过、什么算失败） | 实现判据 |

所以判断"你有没有学会"的标准只有一个：**能不能用自己的话讲清每个文件在干什么、为什么这么分。**
不是"会不会写代码"。

## 8. 关于"要不要做个前端"

**MVP 阶段：不要。** 理由：
- 成绩单是 Markdown 文件，打开就能看，足够验收
- 前端会多花 2 小时，而这 2 小时用在"分流规则"上收益高得多

**投递之后（v1.5）值得做**，而且要做得极简：
一个页面 + 一个下拉框（选 target）+ 一个"开始测试"按钮 + 一张结果表。
在 Flask 里加两条路由 + 一个 HTML 即可（约 60 行），因为你项目里已经有 Flask 和前端经验。

**它的真实用途**：面试演示时不用敲命令行，点一下就出结果，还能截图放进 README。
