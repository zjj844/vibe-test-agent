## 一、项目定位（一句话）

> **AI 增强的接口自动化测试工具**：用大模型按"需求 + 接口契约"生成 pytest 用例，

## 二、简历条目：标题 + STAR 化写法

### 2.0 先纠正一个常见误解

**STAR 是面试讲故事的框架，不是简历排版格式。**

| | 简历（写） | 面试（说） |
|---|---|---|
| 目的 | 3 秒内让 HR/面试官判断"值得聊" | 60 秒内让对方相信"这人真做过" |
| 结构 | **结果前置 + 关键决策 + 可验证数字** | S 背景 → T 目标 → A 行动 → R 结果 |
| 篇幅 | 每条 ≤ 2 行 | 每条 30~60 秒 |

简历上如果把 S/T 完整写出来（"为了提升测试效率，我调研了…"），会挤掉真正值钱的
"我做了什么决策 + 结果是什么"。正确做法是：**把 STAR 压缩成"做了什么 → 关键决策 → 结果"**，
S（背景）交给项目标题那一行，T（目标）交给 jd 关键词，A/R 写进 bullet。

### 2.1 标题怎么写（三段式）

```
项目名（一句话定位）              ← 让人知道这是什么东西
个人项目 | 时间 | 技术栈          ← 让人知道规模和真实性
```

**候选标题（推荐第 2 个）：**

1. ~~AI 接口自动化测试平台~~ —— ❌ "平台"两个字会被追问：有调度吗？有前端吗？多租户吗？都没有。
2. ✅ **AI 增强的接口自动化测试工具 —— 契约驱动 · 有界自愈 · 语言无关**
3. **基于大模型的测试用例生成与自愈工具（Vibe Coding 实践）** —— 想贴 JD 关键词时用这个

**最终写法（照抄）：**

```
AI 增强的接口自动化测试工具 —— 契约驱动 · 有界自愈 · 语言无关
个人项目 | 2026.11 | Python · pytest · DeepSeek API · 220 项自动化测试
```

为什么这么写：`契约驱动 / 有界自愈 / 语言无关` 三个词各自对应一个可追问的技术点
（JSON 契约、≤2 轮 + 6 类分流、同一套工具测 Python 与 Java），
面试官顺着哪个词问，你都有料 —— 这叫**标题留钩子**。

### 2.2 三条 bullet（结果前置，STAR 已压进去）

> 每条格式：**做了什么 + 一个关键决策（为什么）+ 可验证结果**

**B1｜AI 测试用例生成 + 静态质量门禁**
用 DeepSeek 按"需求文档 + 接口契约"生成 pytest 用例，把请求助手与契约断言固化为模板、
**模型只写测试函数**；生成后跑 4 道静态检查（语法 / 用例函数 / 接口白名单 / 返回对象成员白名单），
把"跑一次才知道"的错误拦在毫秒级 —— 实测拦下过模型虚构 API（把 `json_body` 写成 `json()`）。

**B2｜有界自愈：先定义"哪些不许修"，再谈怎么修**
实现"探→读→写→校验→评→快照→跑→分→定→报"闭环，**控制流全在代码里**、模型只负责
"写""评""兜底归因"三个调用点，因此流程可复现、可审计、可单测；失败用有序规则分 6 类并绑定唯一动作
（停手 / 出缺陷报告 / 重写 / 修），自愈上限 **2 轮**；**命中系统 Bug 时禁止改测试** ——
避免把缺陷改成"预期行为"（藏 Bug 比漏测更糟）。

**B3｜契约驱动、语言无关，已跨语言验证**
被测项目用一份 JSON 描述（路径 / 期望状态码 / 期望字段值 / 查询参数 / 是否带登录态 / 需求文档目录），
**加一个项目 = 加一个 JSON**；同一套工具已跑通 **Python(Flask)** 与 **Java(Spring MVC/SSM)** 两个真实项目，
后者需 Bearer 登录，token 由工具层自动获取注入、生成用例的模型不接触 token；
220 条离线测试全绿，报告与生成用例留档在仓库 `docs/samples/`。

### 2.3 同一件事的 STAR 口述版（面试用，约 40 秒）

> 面试官问"介绍一下你这个项目"时，照这个顺序说：

- **S（背景）**：我大三，在自学过程中发现一个问题 —— AI 能很快写出测试代码，但写出来的东西经常跑不起来，
> 而且一旦跑失败，没人分得清是"测试写错了"还是"服务真有 Bug"。
- **T（目标）**：所以我想做的不是一个"能生成测试"的玩具，而是一个**能对自己的产出负责**的工具：
> 生成后要能自己校验、自己跑、失败后能归因，并且**有边界**，不能无限改下去。
- **A（行动）**：我把流程拆成 11 个模块，控制流全写在代码里，模型只保留"写用例""按 rubric 打分"和"规则判不了时的兜底归因"三个调用点；
> 失败用正则规则分 6 类、每类绑定唯一动作；命中"系统 Bug"就只出报告、绝不改测试；"HTTP 200 但数据不对"则挂起交人确认；自愈最多 2 轮，每轮改前先快照。
- **R（结果）**：现在它跑通了 Python 和 Java 两个项目，各自 3/3 通过，其中一次自动生成的用例直接
> 断言了"未登录取分类树必须返回 code=401"这条安全边界；项目有 220 条离线测试，我还把踩过的 8 个坑写成了文档。

## 四、三个必答问题（面试官一定会问）

**Q：为什么不用 crewAI / LangChain Agent / 多 Agent？**
三个触发条件一个都没满足：流程是否**需要动态规划**（否，步骤固定）；是否**需要多角色协作**（否，三个受控调用点足够）；
失败是否**廉价且允许自由探索**（否，测试工具一自由就会乱改测试）。上了框架，调试从"看一个断点"变成"看一段推理文本"，
复现率从 100% 掉到"看运气"。**我的场景要的是可信，不是看起来智能。**

**Q：为什么不用向量数据库 / Chroma？**
需求文档只有 3 篇（22 块），检索质量靠"按标题层级分块"就能解决；引入向量库只增加部署与调试成本。
更关键的是：这一层的接口是干净的可替换点（`RequirementKB`），想换真向量只改一个类 —— **不为用而用**。

**Q：模型会不会为了通过而把断言改弱？**
三层防线：① 分类决定动作（系统 Bug 类根本不给"改测试"这个动作）；② 给模型的失败摘要只含"可修类"，
系统缺陷绝不回喂（否则等于提示它"改断言就过了"）；③ 轮数上限 2，压缩反复弱化断言的空间。

### 8.1 完整版（正式表述）

**AI 增强的接口自动化测试工具（契约驱动 · 有界自愈 · 语言无关）**
个人项目 ｜ 2026.11 ｜ 独立开发

**项目简介**
针对大模型生成测试代码质量不稳定、用例失败后难以定位责任主体的问题，设计并实现一套与开发语言无关的接口自动化测试工具。工具以需求文档与接口契约为输入，通过大模型生成 pytest 测试用例，并在生成后执行静态校验、执行后执行失败分类，配合有界自愈与快照回滚机制形成完整闭环。已完成对 Python（Flask）与 Java（Spring MVC + MyBatis-Plus）两类真实服务的端到端验证。

**技术栈**
Python 3.13 · pytest（junitxml 结构化结果解析）· requests · DeepSeek API（生成侧使用 `deepseek-flash`，评分侧采用低温度采样）· JSON 契约驱动 · 自实现检索组件（标题层级分块 + 哈希向量，无外部向量库依赖）· 有序正则规则引擎 · SQLite 持久化向量索引 + BM25 混合检索 · GitHub Actions（py3.10/3.13 双版本 CI） · `dataclass(frozen)` 不可变数据模型 · SHA-256 清单快照与回滚 · Python 标准库 `http.server` · Vue 3（全局构建，零 npm）· Markdown 报告生成 · Git
（被测服务技术栈：Flask；Spring MVC + MyBatis-Plus + MySQL）

**主要工作**
1. **用例生成与静态校验**：将请求封装、契约断言、鉴权注入等确定性逻辑下沉至固定模板，模型仅输出测试函数，以缩小生成结果的不确定性；落盘前执行四项静态校验（AST 语法解析、用例函数存在性、接口标识白名单、返回对象成员白名单），将仅在执行期才会暴露的缺陷提前拦截在毫秒级，静态校验未通过时携带违规原因定向重试一次。
2. **流水线编排与有界自愈**：设计并实现「探测—检索—生成—校验—自评—快照—执行—分类—决策—报告」十阶段流水线；控制流由代码固化，模型仅承担用例生成与质量评分两项职责，保证流程可复现、可审计、可单元测试；失败按六类分类并映射至唯一处置动作（含「服务端缺陷只出报告」「契约与实现不一致则挂起交人」），自愈轮次上限为 2 轮，每轮变更前生成可校验、可回滚的快照。
3. **失败归因约束**：建立"服务端缺陷不得通过修改测试规避"的硬性约束——服务端 5xx 仅生成缺陷清单并终止自愈；"HTTP 200 但响应值与契约不符"单列为「契约与实现不一致」，处置动作为挂起、交人确认（可能是服务错、契约错或用例错，三者只有人能分清）；仅脚本类与断言类失败允许自动修正，防止将缺陷固化为预期行为。
4. **契约驱动与鉴权透传**：以 JSON 契约描述被测服务的请求方法、路径、期望状态码、期望字段值、查询参数、鉴权要求及需求文档目录，新增被测服务仅需新增契约文件，工具代码无需改动；访问令牌由工具层统一获取与注入，生成阶段不向模型暴露凭证信息。
5. **AI 使用的边界**：模型仅出现在三个受控位置——生成用例（受模板与四项静态校验约束）、质量评分（不接入控制流）、以及**仅当规则无法判定时的兜底归因**（只输出责任判断与建议，无任何动作权限）；规则命中的失败一律不咨询模型。
6. **需求检索与质量评估**：需求文档与外部规范（17 篇 / 157 块）一起按标题层级分块（300 字 / 60 重叠），入 SQLite 持久化向量索引，BM25 + 向量 RRF 混合检索 Top-3 注入提示词，并给外部规范保留 1 个检索配额；对两组标注查询做检索评测（改述型 recall@3 87.5%、MRR 0.792），明确瓶颈在 embedding 能力而非融合策略；用例质量采用五维度 rubric 评分，双采样取中位数以抑制评分波动。
7. **本地报告台与工程化交付**：以 Python 标准库 `http.server` + Vue 3（全局构建、零 npm、无构建链）实现只读报告台，
   支持历史报告列表、Markdown 渲染详情、一键触发单次运行并实时展示流水线各阶段；
   接口层对报告名做白名单校验以防目录穿越，服务仅监听 `127.0.0.1`；边界明确限定为"查看器"而非"平台"（无调度、无账号、无多租户）；配套 GitHub Actions CI（Python 3.10 / 3.13 双版本：编译检查 → 契约自检 → 离线测试）与本地自检脚本，保证"clone 下来即可验证"。
8. **实施成效**：内置两种坏法（5xx / 200 但数据错）的示例服务可一键复现，前者出缺陷清单、后者挂起交人（均未修改任何测试），并可附一段 AI 责任判断供参考；离线单元测试 220 项全部通过；真机覆盖 3 个真实项目（Flask / Spring MVC / JSP+Tomcat），自动生成的用例覆盖了未授权访问鉴权边界（HTTP 200 且响应体 `code=401`），并真实发现一处「PRD 要求登录返回权限码集合、接口未返回」的需求-实现不一致，工具判为需人工裁决而非改测试；沉淀设计自测题 30+ 项与问题记录 8 项。

- **失败归因约束**：服务端 5xx 仅出缺陷清单并终止自愈；"200 但数据不符"单列为契约与实现不一致，处置为挂起交人；仅脚本与断言类失败允许修正，防止缺陷被固化为预期行为。
- **实施成效**：离线单元测试 220 项通过；已跨 Python(Flask) / Java(Spring MVC) / JSP+Tomcat 三类真实服务验证，自动生成用例覆盖未授权访问鉴权边界；内置两种坏法的示例服务可一键复现缺陷报告。

> 定位：**次要项目**，占版面 1/3，作用是证明"我懂后端"。真正要展示的是第九章前面的测试工具。

### 10.1 简历条目（3 行，直接粘贴）

**CMS 内容管理系统（SSM）** ｜ 课程设计 ｜ 负责：接口契约梳理与自动化回归

梳理 7 个核心接口的请求/响应契约（状态码、必填字段、错误码语义），补齐未登录鉴权边界用例；用自研接口测试工具接入本项目完成 3 轮回归，用例 3/3 通过并输出报告。

### 10.2 可选加一句（真想显得有分量时）

> 参与分类模块接口实现：多级分类树查询与增改，删除时校验子分类与文章引用，拒绝产生悬空数据。

### 10.3 这个项目到底是干什么的（**面试口述用，别写进简历**）

**对外行一句话**：就是一个网站后台——编辑在里面写文章，管理员审核通过后文章才能发布出去；谁能看到什么、能干什么由角色权限控制；所有操作都留日志。

**对技术面试官一句话**：基于 SSM 的内容管理后台，提供基于角色的接口鉴权、文章审核状态机、多级分类管理与操作审计，全部接口统一 `Result` 响应。

**三个业务闭环（背这三句就够）**

1. **内容闭环**：新增文章 → 待审核 → 管理员审核 → 发布 / 下架 / 驳回；编辑修改已发布文章会重新进入待审核。
2. **权限闭环**：用户 → 角色 → 权限点（如 `article:add`），接口层用注解 + AOP 校验；**登录了不等于有权限**。
3. **审计闭环**：新增/编辑/删除/审核等关键操作自动写操作日志（模块、动作、操作人、IP），出问题能追到人。

**功能表（按角色看最清楚）**

| 模块 | 能干什么 | 谁在用 |
|---|---|---|
| 登录 / 鉴权 | 账号密码换令牌，令牌放请求头；未登录一律拒绝（`HTTP 200 + code=401`） | 所有人 |
| 文章管理 | 分页查（标题/分类/状态）、详情（浏览量+1）、写、改、逻辑删除 | 编辑 |
| 文章审核 | 审核 = 发布 / 下架 / 驳回，状态 2 / 3 / 0 | 管理员 |
| 分类管理 | 多级分类树、增改删；有子分类或文章时不允许删除 | 管理员 |
| 用户管理 | 分页、启用/禁用、分配角色 | 管理员 |
| 操作日志 | 分页查看谁在什么时候干了什么 | 管理员 |

预置账号：`admin`（超级管理员）、`editor`（内容编辑）、`viewer`（访客），密码均为 `123456`；共 8 张表（用户/角色/权限及其关联、分类、文章、操作日志）。

**30 秒口述版**

> "它是一个内容管理后台，核心是文章的审核流转：编辑写稿、提交审核，管理员决定发布还是驳回；分类是多级的，删分类会校验有没有子分类或文章挂着。
> 权限上不是登录就行，而是用户→角色→权限点三级，接口层用注解加 AOP 校验；
> 所有关键操作都会自动记一条操作日志，能查到人。
> 技术上用 Spring MVC + MyBatis-Plus，八张表，全部接口统一返回 `{code, msg, data}`，未登录统一 `code=401`。"
