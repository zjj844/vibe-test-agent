## 零、面试官的四种动机（先想清楚他在验证什么）

| 他在验证 | 会怎么问 | 你要给的东西 |
|---|---|---|
| **是不是你做的** | "这个契约文件你写的？""跑一次给我看看" | 具体的坑、具体的命令、具体的失败 |
| **理解有多深** | "为什么是 2 轮不是 5 轮？" | 一条能说出口的判断依据 |
| **有没有边界意识** | "那如果……呢？"（追问边缘情况） | 承认边界 + 说明为什么这样划 |
| **能不能带** | "你大三，零基础？""这些你多久学会的？" | 诚实 + 方法论（不是"我很努力"） |

**核心策略：所有答案都落到"我怎么判断的"，而不是"我做了什么"。**

## 一、项目主线（几乎 100% 会问）

### 1. 简单介绍一下你这个项目。

**锚点**：60 秒版——问题 → 做法 → 结果。

**参考回答**：
"这个项目起源于一个我切身体会到的问题：AI 帮我写代码很快，但它写出来的**测试**我不敢信——失败了也说不清是测试写错了还是程序真有 Bug。所以我做了一个自愈测试 Agent：它读取被测项目的接口契约和需求文档，自动生成 pytest 测试，跑完之后对失败做分类——测试自己的错就备份后自动修复，程序真坏了就出缺陷报告给人。目前它已经对两个不同技术栈的项目跑通了——Python 的 Flask 和 Java 的 Spring，并且带着 127 条离线自测。整个过程我和 AI 协作完成，但每个设计决策我都要求自己能讲清楚。"

### 2. 它到底解决什么问题？

**锚点**：三件事——不知道测什么 / 失败不会归类 / 重复犯同一个错。

**参考回答**：
"具体解决三件事。第一，'不知道该测什么'——它用检索从需求文档里捞出业务规则，而不是凭模型瞎猜；第二，'失败不会归类'——传统跑测试只告诉你红还是绿，它会把失败分成六类，明确告诉你这个失败是测试的错还是系统的错；第三，'重复犯同一个错'——它有轮数上限和改前快照，保证 AI 修复是可控的、可回滚的，不会越修越乱。"

### 3. 为什么要做这个？不做行不行？

**锚点**：直接跑 pytest 也行，但那只是"执行"，没有"归因"。

**参考回答**：
"直接跑 pytest 当然行，我自己也每天跑。但 pytest 只负责'执行'，失败之后怎么定位、该谁去修，这些还是要人来。我做的这个工具补的是'归因'这一层——失败发生时它先判断责任在哪边，只把该自动修的部分自动修掉。所以它不是替代 pytest，而是叠在 pytest 上面的一层判断。"

### 4. 现在能测什么、不能测什么？

**锚点**：能——有 HTTP 接口 + 能写契约的项目；不能——UI 自动化、压测、自动修系统 Bug。

**参考回答**：
"能测的是任何'用 HTTP 说话'的服务，只要我给它一份接口契约 JSON——我已经实际测过 Python 的 Flask 和 Java 的 Spring，工具对它们完全一视同仁。不能测的我也想清楚了边界：UI 自动化、性能压测不做，系统 Bug 自动修更不做——那是刻意的，因为让 AI 修系统 Bug 的风险远大于收益。这个边界是设计出来的，不是没做完。"

### 5. 给我看一次运行。

**锚点**：`python demo/buggy_service.py` + `python -m selfheal.loop --target demo-buggy --n 3`，30 秒出缺陷清单。**在家练熟。**

**参考回答**（边操作边说）：
"好，我现场跑一次。先起一个故意有 Bug 的示例服务，然后用一条命令让 Agent 对它做完整的'生成→执行→分流→报告'流程。大家可以看到 30 秒左右它会输出一份缺陷清单——注意它没有去改测试让结果变绿，而是把系统 Bug 如实报了出来，这就是我说的安全边界。"

## 二、设计取舍（最容易被追着问，也是最能加分的地方）

### 6. 自愈为什么最多 2 轮？

**锚点**：收益递减 + 成本翻倍 + 逼它它就会作弊 + 最坏耗时可估算。

**参考回答**：
"主要四个理由。一是收益递减：第一轮修不好，第二轮再修不好，说明问题大概率不在测试这边，多试几轮也不会好。二是成本可控：每轮都是真实的模型调用，轮数上限就是成本上限，最坏耗时可以估算。三是最关键的——如果逼着它无限修下去，它会发现'把断言改宽'是唯一稳过的动作，等于教它作弊。四是工程上需要确定性：固定上限让整个流程可复现、可测试。"

### 7. 模型会不会把断言改弱蒙混过关？

**锚点**：三层防线——分类决定动作 / 反馈只喂可修类 / 轮数上限 2，外加 HOLD 挂起交人。

**参考回答**：
"防了三层。第一层是分类决定动作：如果失败被判定为系统 Bug，模型根本拿不到'修改测试'这个选项，想改也没权限。第二层是信息隔离：喂回给模型修复的反馈，只包含可修类别的失败，系统 Bug 的细节它看不到，无从'针对'。第三层就是刚才说的 2 轮上限。另外还有一个 HOLD 状态：遇到'HTTP 200 但数据不对'这种说不清的情况，工具不改也不猜，直接挂起交给人。"

### 8. 系统返回 500，你为什么不改测试让它变绿？

**锚点**：能改的只有"我看错"，改不了"它确实坏了"；改断言 = 把缺陷固化。

**参考回答**：
"因为改断言解决不了任何问题。500 意味着服务端真的崩了，这是被测程序的问题——如果我把断言改成'500 也算通过'，缺陷不但没修，还被固化成了'预期行为'，以后再也不会被报告出来。这比漏测更糟。所以我的原则是：自愈能修的只有'我看错了'——路径写错、字段名不对这类；'它确实坏了'必须留给缺陷报告。"

### 9. "HTTP 200 但数据是错的"你怎么处理？

**锚点**：单列"契约与实现不一致"，动作 HOLD——不改、不重写，交人确认。

**参考回答**：
"这种情况我单独设了一个类别，处理动作叫 HOLD：不自动修、不重新生成，直接挂起交给人。原因是这时候有三种可能——服务返回的数据错了、契约写错了、测试用例写错了——只有人能结合业务判断是哪一种。让 AI 在三种可能性里蒙一个，蒙错的代价是把错的当成对的。所以宁可停下来等人。"

### 10. 为什么不直接让模型自己决定调哪个工具（tool calling / Agent）？

**锚点**：不可复现、不可审计、不可单测。控制流全在 `loop.py`。

**参考回答**：
"我刻意没用 tool calling，控制流全部写死在主循环里。理由是测试工具最需要的三样东西——可复现、可审计、可单测——恰恰是'模型自主决策'会破坏的：同样输入可能走出不同路径，出了问题没法定位，也没法写单元测试锁住行为。模型在我的架构里只负责两件事：生成测试内容、给修复建议，'什么时候做什么'永远由代码决定。"

### 11. 失败了之后，你怎么知道是被测服务的错还是自己代码的错？

**锚点**：六类规则 + 有序匹配（严重→轻），判不了的才问模型，且模型只给建议。

**参考回答**：
"用的是规则先行：我定义了六类失败，每类都有可机器判定的判据——比如 5xx 对应系统 Bug、连接错误对应服务没起来、语法错误对应生成代码问题——按从严重到轻的顺序匹配。绝大多数失败规则就能定位，只有规则判不了的少数情况才问模型，而且模型只给建议、不给决定权。这样保证了归因结果是确定性的，不是模型每次猜的。"

### 12. 快照和 git 有什么区别？

**锚点**：git 管人写的代码；快照管程序运行期生成的产物，带 sha256 可验证回滚。

**参考回答**：
"职责不同。git 管的是人写的源代码；而 AI 修复时改的是运行期生成的产物——生成的测试文件、快照目录，这些本来就不该进 git。快照是程序自己做的：每次修改前自动备份，带哈希校验，保证回滚回来的内容没被篡改。相当于 git 管长久的版本历史，快照管'这一次修改后悔药'，两者不冲突。"

## 三、AI / LLM 技术（70% 会问，因为投的是 AI 岗）

### 13. 你用了什么模型？为什么用它？

**锚点**：DeepSeek；生成用 flash（省钱、约 13 秒/次），评分用低温度（要可复现）。

**参考回答**：
"用的是 DeepSeek，但两个环节用了不同的配置。生成测试用 flash 版本，因为它调用便宜、速度大概 13 秒一次，适合多轮循环；评分环节用低温度，因为评分要的是稳定——同一个测试两次打分结果应该一致，温度高会引入随机性。这个'按环节选配置'本身就是个设计点。"

### 14. 为什么不用 LangChain / CrewAI / LangGraph？

**锚点**：三条判据一条没满足——流程固定、无多角色、失败代价高。

**参考回答**：
"我的判断标准是三条：流程是不是不确定的、需不需要多角色协作、失败的代价高不高。我的流程是固定的十步流水线，没有多角色，但失败代价高。前两条不满足，说明引入框架解决不了我的问题；第三条满足，但恰恰要求我放弃框架的黑盒——因为出了错我必须能精确知道是哪一步坏了。所以结论是：框架适合'流程不确定'的场景，我的场景不适合，这跟'框架好不好'无关。"

### 15. 为什么不用向量数据库（Chroma 等）？

**锚点**：语料仅十余块，内存检索够用；接口留成可替换点，要换只改一个类。

**参考回答**：
"算了一笔账：我的需求文档切完块只有十几个，这个规模下内存里直接算相似度就够准够快，引入向量数据库是纯粹的运维成本——要多装服务、多管数据，收益是零。但我把检索做成了接口隔离的：知识库是一个独立类，哪天真要换向量库，只改这一个类，其他代码不动。所以准确说不是'不用'，是'现在不需要，且留了位置'。"

### 16. RAG 在你项目里干什么？

**锚点**：只干一件事——把"该测什么"从需求文档里捞出来喂给生成。注意区分 RAG 技术和另一个 RAG 仓库。

**参考回答**：
"它只负责一个环节：生成测试之前，从需求文档里检索出'这个接口相关的业务规则'，告诉模型该测什么——比如需求里写了'不存在的文章要返回 404 不能返回 500'，没有这条信息，模型只会测'接口能不能通'，有了它才会测'业务对不对'。要说明的是，这是 RAG 技术的一次应用；我自己还有一个独立的 RAG 问答项目，那个是被这个工具测试的对象之一，两者不要混淆。"

### 17. 模型幻觉你怎么防？

**锚点**：模板固定 import/URL/鉴权注入 + 4 道静态校验（接口 id 白名单、返回对象成员白名单），编不出契约里没有的接口。

**参考回答**：
"思路是'不指望它不幻觉，而是让它幻觉了也过不了关'。Prompt 模板里把 import、URL、鉴权这些都写死，模型只填业务逻辑部分；生成之后有 4 道静态校验，比如接口 id 必须在契约白名单里、断言引用的字段必须契约里真的有——它编一个不存在的接口，代码活不过静态检查这一关。所以幻觉最多浪费一次生成，不会污染下游。"

### 18. prompt 你怎么写的？

**锚点**：system 写死纪律（只输出测试函数、禁硬编码 URL、禁 skip、禁吞异常），user 给具体任务；失败摘要单独回喂，不塞 system。

**参考回答**：
"分两层。system 层写的是'纪律'——只允许输出测试函数、禁止硬编码 URL、禁止用 skip 跳过问题、禁止吞异常，这些是所有项目通用的规矩；user 层才是'任务'——这个项目的契约、相关需求片段。另外失败后的反馈是单独回喂到对话里的，不塞进 system——因为失败信息每次都不同，塞进 system 会污染后续所有调用。"

### 19. 评分（rubric）为什么不让模型自己定标准？

**锚点**：标准必须人定，否则它给自己宽松标准，分数就没意义。模型只按 1/3/5 锚点打分。

**参考回答**：
"因为裁判不能自己定规则。如果让模型自己决定'什么是好测试'，它会倾向于给自己宽松的标准，分数就失去了参照意义。所以评分标准是人定义的，分三个锚点档——1 分、3 分、5 分各代表什么水平写得清清楚楚，模型只负责'对号入座'打分。这样分数才有可复现性，也才有资格参与'不及格就重新生成'的决策。"

### 20. 两次采样取中位数，为什么不是平均？

**锚点**：抗离群值；两个样本时中位数偏保守。

**参考回答**：
"因为平均会被离群值拉偏。如果模型某一次抽风给了个异常高分，平均分会被它抬高，而中位数直接无视极端值——两次采样时取的就是较低的那个，天然偏保守。对'不合格就重新生成'这种决策来说，保守方向错判的代价远小于放水方向，所以我选中位数。"

## 四、测试基本功（60% 会问）

### 21. 单元测试 / 集成测试 / E2E 的区别？你的项目里各在哪？

**锚点**：127 条离线测试是单元级（用替身）；三次真机跑是 E2E。

**参考回答**：
"按被测范围分：单元测试测一个函数或类，集成测试测几个组件拼起来，E2E 测整条链路。我的 127 条自测基本是单元级——模型、网络全用替身替掉，所以离线能跑、不花钱、速度毫秒级；而'真实起一个服务、完整走一遍生成到报告'的验证是 E2E，我不会经常跑，但每次改动后必须跑。"

### 22. 怎么保证测试本身是对的？

**锚点**：先有人写的基线测试（3 条标准答案）当尺子；静态检查；最后才是 AI 生成。

**参考回答**：
"靠'尺子先行'。我先手写了 3 条基线测试作为标准答案——它们对了，才证明契约解读、执行、分流这条链路是对的；然后是 4 道静态校验拦住结构性的错；最后才轮到 AI 生成。也就是说 AI 生成的测试永远跑在被验证过的轨道上，而不是直接上生产。"

### 23. junitxml 是什么？为什么不用终端输出？

**锚点**：结构化机读报告；解析文本等于拿正则赌措辞（因此得到过假绿）。

**参考回答**：
"junitxml 是 pytest 支持的一种结构化测试报告格式，机器可以直接解析出每条用例的结果。我踩过的坑是：最初解析终端文本判断通过与否，措辞一变就误判，甚至出现过'实际失败但被当成通过'的假绿。换成结构化格式后，'通过/失败'是一个明确的字段，不再依赖任何文本措辞——这也是个教训：能解析结构化数据，就不要解析给人看的文本。"

### 24. 测试要能在无人环境跑，你做到了吗？

**锚点**：模型和服务全用替身，CI 在 py3.10/3.13 上跑 127 条。

**参考回答**：
"做到了，判据就是 CI。我把 127 条测试放进 GitHub Actions，用 3.10 和 3.13 两个 Python 版本跑——CI 环境里没有真实模型、没有真实服务，全靠替身，照样全流程通过。'无人值守能跑'不是我说的，是 CI 每次都在证明的。"

### 25. 你会不会写自动化测试？写过多少？

**锚点**：127 条自测 + 生成的用例若干；如实说"自测为主，业务项目经验少"。

**参考回答**：
"如实说：这个项目里我积累的是 127 条自测加上 Agent 生成的用例，覆盖的是我自己工具的测试。业务系统的测试经验还少——这也是我投实习岗的原因，想在真实业务里把这套方法验证一遍。但'测试要可归因、要能无人跑'这些工程习惯，我已经在这个项目里养成了。"

## 五、工程与协作（50%）

### 26. 为什么分成这么多模块？一个文件写完不行吗？

**锚点**：每个模块只做一件事，模块间单向依赖，各自可测；出问题能定位到模块。

**参考回答**：
"技术上写得完，但维护不了。拆成模块后每个文件只做一件事、依赖方向单一，好处有两个：一是 127 条测试可以按模块独立写，哪个模块坏了测试直接点名；二是出问题时定位是'查模块'而不是'读几千行'。单文件项目唯一省的是建文件的成本，换来的是长期维护成本，不划算。"

### 27. 你的测试跑在哪？CI 怎么配的？

**锚点**：GitHub Actions，矩阵 py3.10/3.13，三步：编译检查 → 契约自检 → 离线测试。

**参考回答**：
"GitHub Actions，配了一个 Python 3.10 和 3.13 的双版本矩阵——这样能提前发现版本兼容问题。每次 push 跑三步：先编译检查语法，再做契约自检，最后跑全部 127 条离线测试。任何一步红了，这次提交就不算数。"

### 28. 前端为什么用 Vue，还零构建？

**锚点**：报告台是"查看器"不是平台；零构建的判据——打开界面要先 npm install，它就从工具变成了项目。

**参考回答**：
"因为需求只是'看报告'，不是'用平台'。我给自己划了一条线：如果一个界面的启动要先 npm install 装一堆依赖，它就从工具变成了另一个项目——维护成本翻倍，还偏离主线。所以报告台用 Vue 但走零构建，浏览器直接打开就能用。这是按用途选方案，不是偷懒。"

### 29. 代码怎么管理版本？有没有分支策略？

**锚点**：一人开发走 main，每个模块一次提交；如实说没有 code review 流程。

**参考回答**：
"一人开发，走 main 加模块化提交——每个模块完成就 commit 一次，commit message 写清楚做了什么，好处是任何改动都能定位到具体提交。诚实地说，没有分支和 code review 流程，因为单人项目上这些是流程成本；如果进团队，这套我会按团队的规范来。"

### 30. 如果两个人同时改这个项目会有什么问题？

**锚点**：如实说——快照/产物目录会冲突、报告台单例运行；没有并发设计（这是刻意的边界）。

**参考回答**：
"会有冲突：快照目录和生成的产物目前按运行实例存放，两个人同时跑会互相覆盖；报告台也是单实例设计。我不会包装成'支持并发'——这是刻意划出的边界，单人工具先把单人的价值做实。真要支持多人，需要给产物目录加会话隔离，这是个明确的改造方向，但不是现在。"

## 附：练习方法（重要）

1. **别背字**——背"锚点"那一行（一句话），完整回答每次用自己的话组织。背字在追问下会崩，锚点不会
2. **自我追问**——每答完一题，想象面试官追一句"为什么？"，接不上就回到对应设计文档补
3. **录音自测**——手机录一遍 60 秒项目介绍，回放听有没有"嗯……那个……"，超过 3 个就再练
4. **诚实三查**——涉及数字、涉及"有没有"、涉及"是不是你做的"，回答前先过一遍诚实红线
