## M1 · 契约与探活（`targets.py`）

### M1-Q1　为什么用 JSON 描述被测接口，而不是把接口地址直接写进测试代码？

**参考答案**
因为「被测对象」和「测试工具」必须解耦。JSON 是**契约**：接口地址、期望状态码、期望字段、业务含义都在里面。换一个被测项目 = 换一个 json 文件，工具代码一行不改。

如果把 `http://127.0.0.1:8000/api/ask` 硬编码进用例，这套工具就只认识这一个项目 —— 而我的核心卖点是「能测 Java CMS，也能测 Flask，工具不认识语言，只认识 HTTP」。

**面试一句**：「被测项目的描述是数据，不是代码 — 加一个项目就是加一个 json。」

### M1-Q2　`ProbeResult` 为什么设计成「只报告、不抛异常」？

**参考答案**
因为「服务没启动」是**预期内的正常情况**，不是程序出错。端口写错、忘了起服务，这些每天都在发生。如果探活抛异常，整个程序崩了，你只看到一堆 traceback，还得自己去猜是不是服务没起。

转成一条人类能看懂的话（`❌ 连接被拒：GET http://.../api/health`）之后，主循环能立刻做出正确决定：**停手，别硬跑**。

**面试一句**：「预期内的失败要变成数据，不能变成异常 — 异常是留给 bug 的。」

### M1-Q3　访问 `127.0.0.1` 为什么要 `trust_env=False`？（我踩过的坑）

**参考答案**
因为 `requests` 默认会读环境变量里的代理（`HTTP_PROXY/HTTPS_PROXY`），把**本机**请求也塞给 Clash 代理。代理连不上时返回 **502**，于是「服务没起」在报告里变成了「服务端返回 502 错误」—— 分类会判成**系统 Bug**，完全带偏。

修法是双保险：`make_session()` 里 `trust_env=False` + 包导入时设 `NO_PROXY=127.0.0.1,localhost,::1`。

**面试一句**：「环境层的问题会伪装成业务层的 bug —— 所以我禁止本机流量走代理。」

## M2 · 需求知识库（`kb.py`）

### M2-Q1　为什么按 H2/H3 标题切块，不用定长切？

**参考答案**
需求文档天然是**按模块组织**的（「查询接口」「答案引用」「拒答行为」各一节）。跟着标题切，每个块语义完整；定长切会把一句话劈成两半，检索出来的片段读不懂，喂给模型就是噪音。

另外块 id 里带着 `#s03`（第 3 节）和 `#c00`（第 0 块），所以任何一条用例都能回溯「它出自需求文档的哪一节」—— 这叫**可追溯**。

**面试一句**：「切块方式决定了检索质量 — 我按文档自身的结构切，不按字数切。」

### M2-Q2　`HashingEmbedder` 这么「土」，为什么不用真模型的向量？

**参考答案**
三个原因：① 离线可跑（CI 里不花钱、不改结果）；② 只有 3 篇需求文档、22 个块，语义检索带来的收益远小于引入一个 embedding 服务的复杂度；③ 这个模块的**接口**是干净的可替换点 —— 想换成真向量，只改一个类。

这就是「不要为了用而用」：检索这块真正的价值是「把该测什么从文档里捞出来」，不是「用了向量数据库」。

**面试一句**：「我评估过收益/成本，这一层用确定性哈希就够，换真向量只改一个类。」

### M2-Q3　检索回来的片段进了提示词，怎么保证模型不是「自己编需求」？

**参考答案**
三道闸：① 提示词里明确「只依据给出的需求片段和契约」；② 生成后**静态检查**必须只用契约里声明过的接口 id（`api("xxx")`）；③ 规则里禁止 skip、禁止兜底 try/except —— 编不出接口就写不下去。

**面试一句**：「不指望模型自觉，靠静态检查兜住。」

## M3 · 用例生成（`generator.py`）

### M3-Q1　模板头（import、`api()` 辅助函数）为什么由我们写死，不让模型写？

**参考答案**
因为那是**每次都必须一模一样**的东西。模型写 import 会飘：有时 `from conftest import api`，有时自己再实现一个 requests 调用，有时漏 import。一旦飘了，错误就发生在「与业务无关的脚手架」上，白白浪费执行时间和重试次数。

所以我们把文件分成两段：**模板头（我们写）+ 测试函数（模型写）**。模型只在「该测什么、怎么断言」上发挥，它不擅长的重复劳动由代码保证。

**面试一句**：「把不变量交给代码，把变量交给模型。」

### M3-Q2　静态检查为什么值钱？（对比：跑一次才能发现的错）

**参考答案**
时间尺度差 3 个数量级：静态检查**毫秒级**，跑一次 pytest 是**秒级**，而且跑 `/api/ask` 这类接口还要真的调模型（我这边单条 2.4 秒）。更关键的是：**跑一次失败，你还要去读 traceback 判断是「代码写错」还是「服务有问题」**—— 而静态检查能判定的错，压根不需要执行。

代价极低、收益极高，这是「能在 1 毫秒内发现的问题，绝不留到 10 秒后」。

**面试一句**：「能在静态阶段拦下的，绝不留到执行阶段 — 便宜一百倍。」

### M3-Q3　`max_repair=1`（同一轮内）和 `max_rounds=2`（跨轮）到底差在哪？为什么两个都要？

**参考答案**

| | `max_repair=1` | `max_rounds=2` |
|---|---|---|
| 触发原因 | **静态检查**不过（用了不存在的字段 `r.json()`） | **真跑**失败（KeyError、断言太严、服务 5xx） |
| 时机 | 生成之后、落盘之前 | 一整轮结束之后 |
| 花的时间 | 秒级 | 几十秒（含真跑） |
| 反馈内容 | 违规文本（「第 12 行用了 r.json()，应为 json_body」） | 失败摘要（用例名 + 失败消息） |

两个都要，因为它们是**两种不同性质的错**：静态错是「语法/契约层面写错了」，能立刻、准确地说出哪里错；运行错是「逻辑/环境层面」，必须跑过才知道。前者便宜，所以允许当场重写一次；后者贵，所以整轮只允许 2 次。

**面试一句**：「重试的粒度跟着成本走 — 便宜的错当场修，贵的错按轮修。」

## M4 · 用例自评（`critic.py`）

### M4-Q1　rubric 的五维标准是谁定的？为什么不让模型自己定？

**参考答案**
**人定的**，写在代码里（`RUBRIC` 字典，每维 1/3/5 三档锚点）。模型只做一件事：按这个表**打分**。

如果让模型自己定标准，它会给自己宽松的标准（「能跑就算 5 分」），那这个分数就完全没意义了。**标准必须是人写的，只有这样分数才可比、可复现、可追责。**

**面试一句**：「标准人定，打分模型给 — 标准一旦交给模型，评估就失去意义。」

### M4-Q2　为什么 2 次采样取**中位数**，不取平均？

**参考答案**
因为模型打分有离群值：同样的代码，一次给 4 分，另一次可能因为措辞偏差给 2 分。**中位数对离群值不敏感**，平均值会被一个极端值拉走。

而且只有 2 个样本时，取中位数 = 取较小那个（保守），这正是评审该有的倾向。

成本上 2 次是可接受的（一次评分约 3 秒）。

**面试一句**：「分数是主观的，所以取中位数抗离群；两次采样是最低成本的一致化。」

### M4-Q3　自评分数低，主循环会做什么？为什么「不」让它「分低就重写」？

**参考答案**
**什么都不做**，只把分数和评语写进报告。循环的继续与否只看**执行结果**，不看分数。

为什么：分数是主观判断，执行结果是客观事实。如果「分低就重写」，等于用模型的自我评价去驱动流程 —— 而模型完全可能写出更弱但「自评更高」的用例（比如删掉边界用例反而更像标准答案）。**把主观信号接进控制流，系统就不可复现了。**

**面试一句**：「评分只用来给人看，不用来驱动流程 — 控制流只认客观事实。」

## M5 · 执行层（`runner.py`）

### M5-Q1　为什么解析 junitxml，而不是解析终端输出？

**参考答案**
终端输出是**给人看的文本**，格式随版本、随参数、随颜色变化，解析它等于用正则赌 pytest 的措辞。junitxml 是**给机器看的结构化格式**（标准格式，CI 系统都在用），字段稳定：每个用例的 `name`、`time`、失败消息、完整 traceback 都在里面。

**面试一句**：「拿结构化数据，别拿渲染后的文本 — 文本是给人看的。」

### M5-Q2　junitxml 里 `<failure>` 和 `<error>` 差在哪？搞错会怎样？

**参考答案**
- `<failure>` = 断言失败（`assert 500 == 200`），或用例函数体里抛了异常
- `<error>` = pytest 在**测试之外**出错：setup/teardown 失败、fixture 报错、收集阶段 import 崩溃

我踩过的真坑：一开始把状态名 `failed` 当成 XML 标签去匹配，而真实标签是 `<failure>`，结果**所有失败都解析成 passed** —— 报告全绿，其实是假绿。假绿是测试工具最严重的 bug，比报错严重得多。

**面试一句**：「XML 标签是 `<failure>`，状态名是 `failed` — 这两个不是一回事，我因为搞混得到过假绿。」

### M5-Q3　为什么要给 pytest 设 900 秒超时？

**参考答案**
被测服务卡死时（比如它的下游模型调用一直挂着），用例会一直等。自愈循环不能陪它一起无限等 —— 这是「**有界**」的又一处体现。

顺带一提：超时之后 `RunResult.error` 会填上说明，主循环判成执行层失败并停手，不会继续拿假数据做决策。

**面试一句**：「有界不只是轮数，还包括时间 — 任何一步都不能无限等。」

## M6 · 失败分流（`triage.py`）

### M6-Q1　5 类失败是怎么判的？为什么用正则不用模型？

**参考答案**
用**有序的正则规则表**判：①服务不可达 → `STOP`　②系统 Bug（5xx）→ `REPORT_DEFECT`　③生成代码问题（AttributeError/NameError/SyntaxError）→ `REGENERATE`　④断言问题 → `FIX`　⑤脚本问题（KeyError/TypeError）→ `FIX`。

不用模型的理由：分类是**决策**，决策必须确定、可复现、可审计。用了模型，同一个失败今天判「脚本问题」明天判「系统 Bug」，那你到底改不改测试就变成了运气。而且正则跑一次是微秒级，模型是几秒。

**面试一句**：「能确定性判定的，一律不问模型 — 这是我整个项目的设计底线。」

### M6-Q2　规则表的顺序为什么必须是「严重 → 轻」？

**参考答案**
因为一条失败文本可能同时命中多条规则。「连接被拒」可能也出现在别的报错里，所以先判不可达最安全。而「接口真返回 500」必须**先于**「断言失败」判 —— 否则会被当成「断言写错了」，于是去改测试，正好把系统缺陷藏起来。

**面试一句**：「规则的顺序本身就是一条设计决策，它决定了会不会误伤。」

### M6-Q3　「服务不可达」为什么是 STOP，而不是重试？

**参考答案**
因为此时**所有**用例都会失败，而且失败的原因与用例质量完全无关。重试既不解决服务没起的事实，还会让每一轮都产生一堆"假失败"，污染统计，甚至诱导自愈去改一堆本来正确的测试。

探活已经做过一次（第 1 步），运行中再次不可达说明服务中途挂了 —— 这时候最正确的动作是停下来，让人去看服务。

**面试一句**：「不可达时改测试是纯粹的破坏 — 先停手，再谈自愈。」

## M7 · 快照（`snapshot.py`）

### M7-Q1　既然有 git，为什么还要自己写快照？

**参考答案**
因为运行期的产物（`evals/generated/`、`.snapshots/`）本来就不进 git（在 `.gitignore` 里）。git 记的是「我认可的代码变更」，快照记的是「这一轮程序自己生成了什么」。

而且快照是**程序在运行时**自动做的，不需要人 `git commit`。要回答「第 1 轮那份代码到底长什么样、能不能退回去」，只能靠快照。

**面试一句**：「git 管人写的代码，快照管程序自己生成的东西 — 两者不能互相替代。」

### M7-Q2　manifest 里为什么要记 sha256？

**参考答案**
为了**可验证**：还原之后能确认「文件内容真的和那一轮一模一样」，而不是「文件名对上了」。记录里还存了 size，两者一起构成指纹。

这也是「回滚点」这个词能站得住的前提 —— 没有哈希，你只能相信复制没出错。

**面试一句**：「回滚必须可验证 — 所以快照记哈希，不只记文件名。」

## M8 · 报告（`report.py`）

### M8-Q1　报告里最重要的不是通过率，是哪一节？为什么？

**参考答案**
是「**缺陷清单**」。通过率只告诉你「这次结果如何」，而缺陷清单告诉你「**接下来该谁去干什么**」—— 哪条用例、命中了什么规则、为什么判成系统缺陷。它是可以直接转成 issue 的东西。

如果报告只有「3 passed」，那它和直接跑 pytest 没有区别 —— **工具的价值在于归因，不在于再打印一次结果。**

**面试一句**：「报告的价值是归因和分工，不是复述数字。」

### M8-Q2　为什么报告要写「每轮做了什么」，而不是只写最终结果？

**参考答案**
因为自愈系统最需要解释的是「**它为什么停下来**」。只写最终 3 passed，你就无法审查它的决策是否合理（它是不是偷偷改弱了断言？它是不是该继续却放弃了？）。

逐轮明细让整条链可审计：生成了几条 → 自评多少分 → 快照在哪 → 跑了什么结果 → 判成什么 → 为什么收工。出问题时，这份记录就是唯一的现场。

**面试一句**：「自愈必须可审计 — 每一轮的判断依据都要留下来。」

## M9 · 主循环（`loop.py`）

### M9-Q1　用例断言 `/api/ask` 返回 200，服务真的返回 500 —— 为什么停下出报告，而不是改测试再跑一次？

**参考答案**
因为让这条用例变绿只有三种改法：改成 `== 500`、删掉断言、加 `skip`。三种改法下 **500 这个错误一个字节都没少，只是从报告里消失了**。这是把缺陷藏起来，比漏测更糟 —— 团队会拿到一张全绿的假成绩单，然后带着 500 上线。

分类决定动作：5xx 属「系统 Bug」，对应动作在设计上就写死是 `REPORT_DEFECT`。只有「测试自己写错了」的那几类才允许改。

**面试一句**：「能改的是『我怎么看』，不能改的是『它怎么样』— 500 属于后者。」

### M9-Q2　为什么最多 2 轮，不是 5 轮、10 轮？

**参考答案**
① 收益递减：第一轮的多是明显错误，喂回报错就能修；再往后剩的是需求歧义/模型能力边界，给 10 次也一样。② 成本翻倍：每轮 = 生成 + 2 次评分 + 一次真跑。③ **最关键：逼它，它会作弊** —— 在「必须通过」的目标下，把断言改弱是唯一 100% 有效的动作，轮数上限本质是在压缩作弊空间。④ 有界可预测：能算出最坏运行时长。

**面试一句**：「轮数上限不是给模型的耐心设的，是给人的原则设的。」

### M9-Q3　`archive_previous()` 和 `snapshot.take()` 有什么区别？

**参考答案**

| | `archive_previous()` | `snapshot.take()` |
|---|---|---|
| 时机 | 跑测试**之前**（落盘时） | 落盘/跑之后 |
| 动作 | 把上一批**挪**进 `_archive/` | 复制进 `.snapshots/` |
| 目的 | **清场**：让 pytest 只收集当前批次 | **存证 + 回滚** |
| 给谁用 | 给机器（pytest 收集机制） | 给人（复盘）+ 给程序（`restore`） |

只留 archive → 回答不了「上一轮那份代码写了什么」；只留 snapshot → 历史文件照样被收集，成绩单是脏的。

（诚实边界：MVP 的自愈是整批重写，所以快照是「每轮回滚点」，不是行级修复记录，那是 v2。）

**面试一句**：「一个管收集，一个管回滚 — 目的不同，都不能省。」

### M9-Q4　为什么把编排写死在代码里，不让模型自由 tool-calling？

**参考答案**
顺序 `探→读→写→校验→评→快照→跑→分→定→报` 写死在 `loop.py`，模型只负责两件事：**写代码**（第 3 步）和**打分**（第 4 步）。其余全是确定性的 Python。

自由 tool-calling 的问题：**不可复现**（同样输入两次跑出不同流程）、**不可审计**（出了事不知道它为什么跳到那一步）、**不可测试**（没法写单测）。而我这份项目的 78 个测试里，有 11 个专门测「决策」（不可达不生成、缺陷不重写、到上限必停）—— 这些都只有在编排是代码时才可能。

**面试一句**：「模型负责创作文本，代码负责控制流程 — 这条边界是我这个项目的核心架构选择。」

## 综合题（面试官一定会追问的）

### Z-Q1　为什么不用 crewAI / LangChain Agent？

**参考答案**
三个触发条件，一个都没满足：① **需要动态规划**吗 —— 不需要，测试流程的步骤是固定的；② **需要多角色协作**吗 —— 不需要，两个调用点（写、评）就够了；③ **失败代价低、允许自由探索**吗 —— 恰恰相反，测试工具一旦自由发挥就会乱改测试。

用 Agent 框架的代价是：调试从「看一个断点」变成「看一段自然语言推理」，复现率从 100% 掉到「看运气」。而我的场景要的正是可信和可复现。

**面试一句**：「框架解决的是『流程不确定』的问题 — 我的流程是确定的，上框架只会增加不确定性。」

### Z-Q2　这个工具最坏跑多久？你怎么保证？

**参考答案**
轮数上限 2 × 每轮（生成 ≤2 次模型调用 + 自评 2 次 + 一次 pytest 900 秒超时）。所以最坏是有界的、可算出来的。

「有界」在四处落地：轮数、单次 HTTP 超时、pytest 整体超时、静态检查不合规就不执行。任何一步都不会无限等。

**面试一句**：「每一层都有上限，所以最坏运行时长可以算出来 — 这是能进 CI 的前提。」

### Z-Q3　如果模型为了通过而把断言改弱，你怎么防？

**参考答案**
三层：① **分类决定动作**：系统 Bug 类根本不给「改测试」这个动作；② **反馈只喂可修类**：系统缺陷绝不写进给模型的失败摘要里，否则等于提示它「改断言就过了」；③ **轮数上限 2**：压缩它反复试错、逐步弱化断言的空间。

另外生成阶段有静态检查兜底（禁止 `skip`、禁止用兜底 `try/except` 吞异常）。

**面试一句**：「防作弊不能靠模型自觉，要靠『不给它那条路』。」

### Z-Q4　怎么把这套工具用到你的 Java CMS 上？

**参考答案**
只写一个 `selfheal/configs/java-cms.json`：`base_url=http://localhost:8080`，把 5 个 controller 里要测的接口按 `id/method/path/expect_status/expect_fields/body/notes` 写进去。然后

```bash
python -m selfheal.loop --target java-cms --n 3 --rounds 2
```

**工具代码一行都不用改** —— 因为它测的是 HTTP，不是 Python。这正是「契约驱动」的兑现：同一个工具测两个语言完全不同的项目。

**面试一句**：「加一个被测项目 = 加一个 json，这就是契约驱动的兑现。」

### Z-Q5　你测出过真的 bug 吗？（诚实答法）

**参考答案**
诚实分三层：
- **工具自身暴露过真问题**：探活因代理变成 502、junitxml 标签写错导致假绿、同秒复用旧报告 —— 这些都在 README/提交记录里有据可查。
- **被测项目**：RAG 端 `/api/ask` 在下游模型不可用时直接抛 500（没有优雅降级），这是真实的健壮性缺陷。
- **不吹的地方**：目前还没有「依靠 AI 生成的用例发现了人手没发现的业务 Bug」这种样本，MVP 阶段主要价值在「持续、低成本地覆盖契约」。

说自己没做到的部分，比编一个故事更让人信。

**面试一句**：「我记录了自己踩的坑，也清楚它现在还没证明的那件事。」
