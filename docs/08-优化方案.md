# 优化方案（已知缺口 + 补法）

> 这份文档是**诚实的路线图**，不是许愿池。每一条都写清：现状 → 为什么是问题 → 怎么改 → 验收标准 → 成本。
> 面试时被问"这个项目还缺什么"，照着说就行——**能说清缺什么，比声称什么都做了可信**。

---

## P0 · 回归沉淀（`promote`）—— 最重要的一条

**现状**：每轮重新生成用例 → 跑 → 归档进 `evals/generated/_archive/`。通过的用例不保留、不累积。

**为什么是问题**（真实发生）：
同一份契约、同一个服务，连跑两次结果不同——
- 第 1 次生成的 login 用例断言了「PRD 要求返回 11 个权限码」→ 红
- 第 2 次生成的 login 用例只断言「有 token」→ 绿

于是**通过率不是质量信号，而是"这次凑巧测到了什么"**。上次发现的需求-实现不一致，下次可能"绿过去"。

**怎么改**：
```
新增 selfheal/promote.py
  python -m selfheal.promote --target cms        # 把本次通过的用例固化
    → 复制到 evals/regression/<target>/*.py     # 固定、不再被重写
    → 写 regression.json 记录：用例名/覆盖接口/断言摘要/来源报告
loop 里第 ⑩ 步之前先跑回归集（确定性），再生成新用例探索新边界
报告新增一节「回归集」：本次回归 X 条全绿 / 失败 Y 条
```

**验收**：同一条断言（如"11 个权限码"）在**每次**运行都被执行，结果稳定；删掉代码里的 perms 必然每次都红。

**成本**：约 40 分钟（含 4~6 条单测）

## P1 · 覆盖稳定性度量（`--repeat N`）

**现状**：一次运行只生成一批用例，看不出"哪些接口/断言是稳定覆盖的"。

**为什么是问题**：LLM 生成有方差。不知道方差多大，就没法判断"这次全绿"有多可信。

**怎么改**：
```
python -m selfheal.loop --target cms --repeat 3
输出：每个接口被覆盖的次数 / 每次的通过率 / 同一接口断言是否一致
→ 报告里给一张「覆盖稳定性」表
```

**验收**：能回答"这个契约跑 3 次，`auth-login` 覆盖 3/3、`category-tree` 覆盖 1/3"。

**成本**：约 30 分钟

## P1 · 契约表达力：`expect_len`

**现状**：`expect_json` 只能比"某路径等于某值"（`"data.total": 798`），比不了集合大小。

**为什么是问题**：PRD 里大量要求是**数量型**的——"admin 必须有 11 个权限码""列表不得为空"。这类要求进不了契约，只能靠模型自己写断言 → 失败后**无法自动定责**（第 2 次运行就可能漏测）。

**怎么改**：
```json
"expect_len": { "data.user.perms": 11, "data.list": ">=1" }
```
`check_contract` 里断言长度；失败消息形如「data.user.perms: 期望长度 11，实际 0」→ 命中分流的"契约与实现不一致"→ **HOLD 交人**，而不是两轮改断言后 gave_up。

**验收**：把 PRD 的"11 个权限码"写进契约后，即使模型不写那条断言，工具也能稳定抓到不一致。

**成本**：约 30 分钟（含校验器 + 模板 + 单测）

## ✅ P2 · 检索层接入生成链路（已完成）

**原现状**：`vectordb.py`（SQLite 持久化索引 + BM25 + RRF 混合）做完了并有评测数字，但 `kb.py` 仍用内存版 —— 外部规范没进生成提示词。

**已完成的做法**：
```
RequirementKB(docs_dir=..., external_dir=..., mode="hybrid")
  → 需求文档 + 外部规范一起切块进 VectorIndex（契约字段 external_docs 指定目录）
  → search() 走 hybrid（向量 + BM25 的 RRF 融合）
  → 给外部规范留 1 个配额（否则纯排序它永远进不了 Top-3）
```
**验收（已达成）**：真机报告里出现 `规范·alibaba-p3c/日志规约#s00` —— 规范条款真的进了提示词。
索引：206 块（需求 49 + 外部规范 157），18 篇文档。

**仍欠的配套**：`HashingEmbedder` → 真 embedding（接口已留：`VectorIndex(embedder=...)`）。
评测显示改述型查询 recall@3 只有 87.5%，瓶颈就在 embedding 能力。

## P1 · 契约"瘦身"自动化（起草时标可跑性）

**现状**：AI 起草出来的契约是**全量接口**（真实项目 18~100 个），其中一半是"需要业务参数的写操作"。
用户必须手工删到 6~10 个，否则跑出来一堆 400/500。（实测：18 接口契约三次里崩三次；8 接口五次要两次全绿。）

**为什么是问题**：这不是"接口多"的问题，是**契约里混了跑不起来的接口**。用户第一次用就会踩。

**怎么改**：起草时给每个接口打标记并默认只勾"可跑"的：
```
✅ 只读、无需参数        → 默认勾选
⚠️ 只读、需要路径参数    → 默认勾选（用示例值）
❌ 写操作、缺 body       → 默认不勾选，提示"需要业务参数"
❌ 需要前置数据          → 默认不勾选
```

**验收**：起草完 18 个接口，表格里默认选中 6~8 个，直接能跑。

**成本**：约 1 小时（与 P3"契约编辑器补字段"合并做）

---

## P2 · 定向自愈（只重写失败用例）

**现状**：第 2 轮是**整批重写**——上一轮已通过的用例可能被改坏或丢失。

**怎么改**：按 nodeid 把失败用例挑出来，只针对它们重写；通过的原样保留（与 P0 的回归集天然配套）。

**成本**：约 1 天（要做"用例→函数边界"的切割与合并，风险最高的一条）

---

## P3 · 断言可追溯（来源标注）

**现状**：用例断言失败时，只有"断言失败"四个字，看不出这条断言**依据哪条需求**。

**怎么改**：生成时要求每条断言带 `# 依据 FR-3` 注释；分流时若失败断言的依据来自 PRD/契约，判「契约与实现不一致 → HOLD」。

**价值**：把"责任判定"从"猜"变成"查得到出处"。

**成本**：约 2 小时

---

## P3 · 契约编辑器补字段

**现状**：前端表格只有 5 列（id/方法/路径/期望码/业务含义）。`auth`、`body`、`no_auth`、`expect_json`、`params` 都得手工改 JSON。

**怎么改**：表格加"请求体 / 是否带登录态 / 期望字段值"三列 + 一个 auth 区域。

**成本**：约 1 小时

## 已修的坑（都来自真机跑出来的事故，不是想象）

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | 报告全绿但其实是假绿 | 拿状态名 `failed` 去匹配 junitxml 标签（真标签是 `<failure>`） | 按 `<failure>/<error>/<skipped>` 解析 + 单测覆盖 |
| 2 | `{code:401}` 被当成"断言写错" | 契约只能断言"字段存在"，测不出"值不对" | 新增 `expect_json`（支持点路径），并加**契约与实现不一致 → HOLD** |
| 3 | 每次都检到别的项目的需求 | 契约没配 `requirements_dir`，退回默认目录 | 保存需求时**自动**给契约补字段；`external_docs` 同理 |
| 4 | 18 接口契约跑出 0% 通过率 | 起草出的契约里 11 个写操作没有 body，且没有 auth | 起草自动补 `auth` + 保存前**契约体检**（四类警告） |
| 5 | 第 2 轮生成报"正文为空" | 提示词变长 → 推理模型把 `max_tokens` 吃光 | 预算 14000 → 空正文自动放大 32000 → 再精简历史 |
| 6 | 外部规范明明在索引里，却一条都检索不到 | ①语料在子目录，`glob` 读不到；②混检时规范永远排不进 Top-3 | ①外部目录用 `rglob`（需求目录不递归）；②给规范留 1 个配额 |
| 7 | 导入面板点开就白屏 | 模板引用了 `app.js` 里不存在的 `reqFiles` | 补字段 + **错误横幅兜底**（不再白屏）+ 模板/JS 一致性测试 |
| 8 | 接入 RAG 后"失败变多"的错觉 | 失败集中在 18 接口契约，与 RAG 无关（数据：8 接口 5 次只红 2 次） | 见 `docs/09` 的"失败变多 ≠ 变差"判断表 |

## 刻意不做（避免变成"平台"）

- 任务调度、多用户、权限体系、历史趋势库
- 分布式执行、并发跑多目标
- 自动修改系统 Bug（红线：**服务端缺陷只出报告**）
- 自建 LLM 网关 / Prompt 管理平台

---

## 一句话总结（面试用）

> "它能生成、能校验、能归因、能出缺陷报告，也接了外部规范的混合检索；
> **最大的短板是'不沉淀'**——通过的用例没有变成回归资产，所以单次通过率不代表质量，
> 我实测就遇到过同一条需求不一致、上一次红、下一次绿。
> 补法已经写进 `docs/08-优化方案.md`：先做 promote（回归沉淀），
> 再做覆盖稳定性度量、契约 `expect_len`、契约瘦身自动化。"
