# 交付物 1（v2）：MVP 架构设计 —— 一个工具，多个被测项目

> v1 是"只测自己的 RAG 后端"。你的诉求改成"**同一个工具，能测我任何一个项目**"，所以架构重写。
> 本次改动只影响"被测对象怎么描述"，生成/执行/分流/报告四步完全不变。

---

## 0. 你的诉求 → 两个关键决定

> "用 rag（或 agent）读取需求，然后生成测试脚本和反馈错误报告，我可以拿它测我的另一个项目（Java CMS）"

由此产生两个决定，都会改变实现细节：

### 决定 1：从"Flask test_client"改成"**真实 HTTP 请求**" ❗

| | v1（test_client） | v2（requests 真实 HTTP） |
|---|---|---|
| 怎么发请求 | 直接在进程内调 Flask | 真的发 HTTP 到 `http://host:port` |
| 语言中立 | ❌ 只能测 Python/Flask | ✅ **Python、Java、任何服务都能测** |
| 前提 | 无需起服务 | **被测服务必须先跑起来** |
| 速度 | 毫秒 | 几毫秒到几十毫秒 |

**必须改**：你要测 Java CMS，而 test_client 只能测 Python 应用。
改了之后，**同一个工具对 Flask 和 Spring 完全一视同仁**——这就是"相辅相成"的技术基础。

### 决定 2：被测对象变成**配置**，不是写死的代码

```
selfheal/targets/
├── rag-backend.json    ← 你的 RAG 后端（Flask，端口 8000）
└── java-cms.json       ← 你的 Java CMS（Spring，端口 8080）
```

工具不认识"RAG"或"CMS"，它只认识 `target` 文件。加一个新项目 = 加一个 json。

## 1. 统一架构

```
        需求文档（RAG 知识库）           接口契约（target json）
        「为什么该这样」                「接口长什么样」
                 │                          │
                 └────────┬─────────────────┘
                          ↓
              ┌───────────────────────┐
              │  Agent 循环（最多 2 轮） │
              │  生成 → 自评 → 执行     │
              │      → 分流 → 修复      │
              └───────────┬───────────┘
                          ↓
        ┌─────────────────┴─────────────────┐
        ↓                                   ↓
   REPORT-时间.md                      .snapshots/（可回滚）
   （通过率/分类/覆盖/缺陷）            （改前备份）
```

**注意左边有两份输入，这是它们的分工（面试会问）**：

| 输入 | 回答什么问题 | 存哪 |
|---|---|---|
| **需求文档**（RAG 检索） | **该测什么**：有哪些业务规则、边界、异常要求 | `kb.py` 现有的需求知识库 |
| **接口契约**（target json） | **怎么调、期待什么**：路径、方法、参数、状态码、字段 | 手写 json（约 40 行） |

> 只有契约 → 你只能测"接口能通"；
> 加上需求 → 你才能测"业务对不对"。**这是 RAG 在这个工具里的正统位置。**

## 2. target 配置长什么样（这是新东西的核心）

```json
{
  "name": "java-cms",
  "base_url": "http://127.0.0.1:8080",
  "health": { "method": "GET", "path": "/api/category/list", "expect_status": 200 },
  "endpoints": [
    {
      "id": "category-list",
      "method": "GET",
      "path": "/api/category/list",
      "expect_status": 200,
      "expect_fields": ["code", "data"],
      "notes": "分类列表，返回 JSON"
    },
    {
      "id": "article-detail-404",
      "method": "GET",
      "path": "/api/article/999999",
      "expect_status": 404,
      "notes": "不存在的文章应返回 404，不是 500"
    }
  ]
}
```

**这 5 个字段就是全部约定**：`method / path / expect_status / expect_fields / notes`。
（`notes` 会被塞进 Prompt，让 LLM 知道这个接口的业务含义。）

## 3. 两个 target 的对照（证明"同一套工具能覆盖两个技术栈"）

| | rag-backend | java-cms |
|---|---|---|
| 语言/框架 | Python / Flask | **Java / Spring MVC** |
| 怎么启动 | `python scripts/serve.py`（8000） | `mvn jetty:run`（8080，需 MySQL） |
| 契约来源 | 手写 json（Flask 无 openapi） | 手写 json（也可从 Spring swagger 生成） |
| 断言风格 | JSON 字段 | JSON 字段（**完全同构**） |
| 前置条件 | 无 | MySQL 3306 + 导入 `sql/cms.sql` |

> 面试价值：**"同一个测试 Agent，能测 Python 的 Flask 和 Java 的 Spring 两个项目"** ——
> 这一句同时命中 JD1（方法论）和 JD2（Java、流程化测试、现有代码改造）。

## 4. 模块划分（8 个，比 v1 多一个 targets/）

| # | 文件 | 干什么（人话） | 输入 | 输出 |
|---|---|---|---|---|
| M1 | `selfheal/targets.py` | **翻译官**：读 target json 成对象，并探活 | target json | `Target` 对象 |
| M2 | `selfheal/kb.py` | **读需求**：按章节切需求文档 + 检索（复用你已有的） | 需求 md | 相关片段 |
| M3 | `selfheal/generator.py` | **出题人**：契约 + 需求片段 + 失败历史 → pytest 用例 | 三者 | `test_*.py` |
| M4 | `selfheal/critic.py` | **自查**：rubric 5 维打分，2 次取中位 | 用例源码 | 分数 + 评语 |
| M5 | `selfheal/runner.py` | **监考**：跑 pytest，解析 junitxml | 测试文件 | 每条用例结果 |
| M6 | `selfheal/triage.py` | **判卷**：失败分 5 类（见 §6） | 失败详情 | `Failure(kind)` |
| M7 | `selfheal/snapshot.py` | **后悔药**：改前备份，一键回滚 | 文件路径 | 快照目录 |
| M8 | `selfheal/loop.py` + `report.py` + `main.py` | **工头 + 报告 + 总开关** | target 名 | `REPORT-*.md` |

## 5. 自愈循环（闭环，可背）

```
探测服务可达 → 读契约 + 检索需求 → 生成用例 → 自评（不及格重生成）
   → 执行 pytest → 分流 → （可修的：备份后修；不可修的：记缺陷）
   → 轮数 < 2 ? 回到"执行" : 出报告
```

**一句话背**：**探 → 读 → 写 → 评 → 跑 → 分 → 修（≤2 轮）→ 报**

---

## 6. 分流规则（v2 从 4 类变 5 类）

| 类别 | 判据（可机器判定） | 处理 |
|---|---|---|
| ① **服务不可达** 🆕 | `ConnectionError` / `ConnectionRefused` / 探活失败 | **不修任何东西**，直接报"被测服务没起来" |
| ② 系统 Bug | 5xx、返回结构与契约不符、401 | 不改脚本，出**缺陷报告** |
| ③ 脚本问题 | 路径写错、字段名不存在、参数缺 | **自动修** |
| ④ 断言问题 | 返回正常但断言值与契约矛盾 | **自动修**（改断言或改契约，二选一并说明） |
| ⑤ 生成代码问题 | `AttributeError` / `SyntaxError` / `TypeError` | **重新生成**该用例，不修原文件 |

**①是 v2 新增的，而且很重要**：v1 用 test_client 不需要它；改成真实 HTTP 后，**"服务没起来"会伪装成"测试全失败"**，必须单独识别——否则自愈会去改一堆根本没问题的用例。

**为什么这是安全边界**（面试必答）：
> 如果模型见到失败就改测试，它会把"接口真坏了"改成"测试通过了"——**缺陷被掩盖，比漏测危险得多**。
> 所以自愈的第一条规则不是"怎么修"，而是"**哪些不许修**"。

## 7. RAG / 向量库在这个工具里的两个位置

| 位置 | 用途 | 现在做吗 |
|---|---|---|
| **需求知识库**（已有 `kb.py`，哈希嵌入） | 检索"该测什么" | ✅ **MVP 就做** |
| **失败记忆**（失败→根因→修法，向量库） | 检索"这个错以前怎么修的" | ⬜ v1.5，第 4 晚，约 150 行，复用 `rag/` 组件 |

**不做的位置**：接口契约检索（4 个接口直接读 JSON 更准，检索是负收益）、Agent 编排（流程确定性，不需要）。
