# REQ-001 · 订单查询接口（demo-buggy）

> 被测服务是 `demo/buggy_service.py`（**故意带 Bug** 的示例服务）。
> 这份需求文档就是"正确答案"，用来对照服务实际行为。

## FR-1 商品列表

`GET /api/items` 返回统一响应体：

```
{ "code": 200, "msg": "操作成功", "data": [ {id, name, price}, ... ] }
```

- `data` 必须是数组；没有商品时返回空数组，不得返回 `null`
- 每个元素必须含 `id`、`name`、`price`

## FR-2 订单详情（正常路径）

`GET /api/orders/{id}` 查订单详情，成功时返回 `code=200`，`data` 含
`id`/`item_id`/`qty`/`status`。

## FR-3 订单不存在时必须返回 404，不得 500

订单不存在时，接口必须返回：

```
{ "code": 404, "msg": "订单不存在", "data": null }
```

**不得**抛出未捕获异常。服务端 500 意味着"查不到数据"被当成了"程序出错"，
这会让前端拿不到可读的错误信息，也会污染监控里的错误率指标。

> 这是本项目最重要的演示点：如果用例断言"应该 200/404"，而服务返回了 500，
> 那么**错的是服务，不是测试**。测试工具不应该为了让成绩单好看去改断言。

## FR-4 订单总价必须等于单价 × 数量

`GET /api/orders/{id}/total` 返回 `{code:200, msg, data:{order_id, total}}`，
其中 `total` = 单价 × 数量（不含运费/优惠，本 demo 不涉及）。

- 41 号订单：2 件单价 399 的商品 → `total` 必须为 **798**
- 返回 `total=399` 属于计算错误（把单价当成了总价）

> 注意：这类 bug 的**状态码是 200**，字段也齐全。只断言"200 + 有 data"
> 是发现不了的，必须断言具体的值。而"值不对"的时候，责任可能是服务、
> 也可能是契约或断言写错 —— 所以本工具在这种情况下选择**挂起交给人**，
> 而不是自动改测试。


## NFR-1 统一响应体

所有接口都返回 `{code, msg, data}` 三字段，`msg` 为可直接展示的中文提示。
